# BeautyBoy — 스킨케어 순서를 모르는 남성을 위한 커머스

이 글은 BeautyBoy 프로젝트의 소개 편이다. 서비스가 무엇이고, 어떤 흐름으로 동작하며, 무엇이 다른지를 다룬다. 만들면서 겪은 문제들(재고 동시성, 락 경합, 토큰 레이스)은 [트러블슈팅 편]에서 다룬다.

## 왜 만들었나

화장품 커머스는 많다. 하지만 대부분은 **이미 뭘 살지 아는 사람**을 위한 곳이다. 검색하고, 필터를 걸고, 리뷰를 비교하는 흐름은 "토너와 세럼 중 뭘 먼저 바르는지"조차 모르는 사람에게는 진입 장벽이다. 그리고 그 사람은 대개 남성이다.

BeautyBoy는 질문을 바꿨다 — "무엇을 살까"가 아니라 **"어떤 순서로 뭘 쓰면 되는데, 그걸 지금 여기서 살 수 있나"**. 상품이 아니라 **루틴(순서)을 판다**는 것이 이 서비스의 정체성이다.

## 기술 스택

| 영역 | 구성 |
|---|---|
| 백엔드 | Spring Boot 3.5 · Java 21 · Spring Data JPA · Flyway · MySQL 8.4 |
| 프론트 | React 19 · TypeScript · Vite · TanStack Query · Zustand |
| 인프라 | Docker Compose · Redis (조회 캐시·조회수 버퍼) · Kafka (주문 후처리) |
| 테스트 | JUnit + Testcontainers(실 MySQL) · Vitest + MSW · Playwright E2E · k6 부하테스트 |

백엔드는 마이크로서비스가 아니라 **모듈러 모놀리스**다. 도메인 패키지(member, catalog, order, payment, ingredient, …)가 각자 자기 테이블만 접근하고 타 도메인은 서비스 인터페이스를 경유한다 — 이 규모에서 배포 단위를 쪼갤 이유는 없지만, 경계는 처음부터 그어 두었다.

## 실행 흐름 — 고민에서 결제까지

대표 플로우 하나를 따라가 보자. "모공이 고민인데 뭘 써야 할지 모르는" 사용자다.

**① 가입 시 피부 프로필** — 피부타입과 고민(모공, 트러블, 보습 등 9종), 선호 사용감(산뜻함/촉촉함/매트)을 고른다. 이 선택이 이후 모든 화면의 개인화 재료가 된다.

**② 메인 — 내 고민이 반영된 루틴 섹션** — 메인의 루틴 5단계(클렌징 → 토너 → 세럼 → 로션 → 선케어) 섹션이 프로필과 행동에 맞춰 재구성된다. 모공이 고민이면 세럼 단계에 모공 케어 상품이, 이유("모공 고민을 고르셨어요")와 함께 뜬다.

![메인 — 개인화된 루틴 섹션](../screenshots/01-main.png)

**③ 루틴 가이드 — 순서를 가르쳐주는 페이지** — 각 단계가 왜 필요한지, 어떤 순서로 쓰는지를 설명하고 단계마다 상품을 추천한다. "아침엔 이 순서, 저녁엔 이 순서"를 모르는 사람이 목차처럼 읽고 그대로 담을 수 있다.

![루틴 가이드](../screenshots/02-routine.png)

**④ 상품 상세 — 성분 궁합 진단** — 상세 페이지에서 성분 구성을 안전/주의 신호로 보여주고, **장바구니에 담긴 상품과 지금 보는 상품의 성분 궁합**(예: 레티놀 × AHA 같은 충돌 조합)을 진단한다.

![상품 상세 — 성분 패널](../screenshots/03-detail.png)

**⑤ 장바구니 → 토스 결제** — 결제는 토스페이먼츠 2단계 검증(클라이언트 승인 요청 → 서버 금액 재검증 후 확정)으로 처리한다. 가격·재고는 이 시점에 서버가 전부 재검증한다.

## 차별점

### 1. 상품이 아니라 순서를 판다

카테고리 트리 대신 **루틴 단계가 곧 내비게이션**이다. "세럼이 뭔지" 몰라도 3단계에 도착하면 지금 사야 할 것이 나온다. 추천의 단위도 상품이 아니라 (단계 × 태그)다 — "다음 단계로 모공 케어 세럼"처럼, 흐름 속의 빈칸을 채우는 방식으로 추천한다.

### 2. 행동 분석을 서버가 아니라 기기에 맡겼다

이 프로젝트의 설계 원칙 중 하나는 **"돈과 재고는 서버, 취향은 클라이언트"**다. 틀리면 사고가 나는 계산(가격, 재고, 주문, 쿠폰)은 항상 서버가 재검증한다. 반대로 틀려도 추천이 조금 어긋날 뿐인 계산 — 취향 — 은 클라이언트에 위임했다.

사용자가 웹에서 한 행동은 서버로 전송되지 않는다. 기기 안에서 점수가 된다.

```
[기기] 상품 조회(1점) · 찜(2점) · 담기(3점)
   → localStorage 이벤트 링버퍼 (최근 50개)
   → (카테고리 × 태그)별 점수 집계
   → 서버가 배포한 규칙 JSON과 대조 → "다음에 볼 (단계 × 태그)" 산출
   → 기존 상품 조회 API 호출 → 렌더
```

서버가 하는 일은 두 가지뿐이다 — **규칙 JSON 배포**(ETag 캐시라 재방문 시 대개 304, 본문 0바이트)와 기존 `/goods` 조회. 사용자별 프로필 저장소도, 행동 로그 수집 파이프라인도, 추천 배치 잡도 서버에 없다.

이 구조가 주는 것:

- **서버 비용 0** — 개인화를 위한 연산·저장·로그 수집이 서버에 존재하지 않는다. 추천 목표 조합이 규칙에서 파생되어 유한하므로(수십 개) 상품 조회는 HTTP 캐시도 잘 먹는다.
- **즉시 반영** — 방금 담은 상품이 네트워크 왕복 없이 다음 화면 추천에 바로 반영된다.
- **프라이버시** — 행동 데이터가 기기 밖으로 나가지 않는다.

그리고 완전한 클라이언트 위임이 아니라는 점이 중요하다. **계산은 기기가 하지만, 규칙의 진실은 서버에 있다.** 추천 규칙(`고민 → 다음 단계 × 태그` 매핑)은 DB에 있고 API로 배포되므로, 규칙을 바꾸면 프론트 배포 없이 메인과 상품 상세의 추천이 동시에 따라온다.

**트레이드오프도 있다.** 기기가 바뀌면 행동 프로필이 따라가지 않고, 첫 방문엔 행동 데이터가 없으며, 전체 유저 데이터를 쓰는 협업 필터링은 불가능하다. 콜드 스타트는 가입 시 받은 피부 프로필이 메우고(첫 방문자도 고민 기반으로는 개인화된다), 기기 간 비동기화는 "추천이 조금 다를 뿐 사고가 아니다"로 수용했다. 수백만 유저의 행동 상관관계를 학습해야 하는 규모가 되면 서버로 옮겨야 한다 — 그때 옮길 수 있도록 신호 수집과 계산이 한 모듈에 격리돼 있다.

### 3. 성분 궁합을 데이터로 진단한다

"레티놀 쓰는 날 AHA 필링은 피하라" 같은 지식은 아는 사람만 안다. BeautyBoy는 식약처 공공데이터(화장품 성분·사용제한 기준)를 시딩한 규칙 엔진으로 이를 자동 진단한다 — 상세 페이지에서는 단일 상품의 성분 주의도를, 장바구니와의 대조에서는 **함께 쓰면 충돌하는 조합**을 알려준다.

판정 임계값은 감으로 정하지 않았다. 카탈로그 1,472개 성분의 주의도 분포를 실측하니 64 / 18 / 10 / 7%로 갈렸고, 경계를 한 단계 올리면 상위 두 단계가 뭉개지고 한 단계 내리면 카탈로그 절반이 경고가 됐다 — 그 사이에서 신호가 살아있는 지점을 골랐다. 규제상 사용제한(LIMIT) 플래그는 점수에서 뺐는데, 카탈로그의 77%가 해당되어 넣는 순간 신호가 죽기 때문이다. 씻어내는 제품은 접촉 시간이 짧아 한 단계 완화한다.

## 마치며

정리하면 BeautyBoy의 차별점은 세 문장이다.

1. **순서를 판다** — 스킨케어를 모르는 사람이 루틴을 따라가면 구매가 끝나 있다.
2. **취향은 기기가 계산한다** — 서버 비용 없이, 즉시, 프라이버시를 지키며. 단 규칙의 진실은 서버가 쥔다.
3. **성분 궁합은 데이터가 판정한다** — 식약처 데이터와 카탈로그 실측 분포로.

만드는 동안 겪은 문제들은 따로 한 편이 됐다 — 재고 100개에 101번째 결제가 성공할 뻔한 이야기, 주문 확정 p95 15.3초의 범인을 추적한 이야기, 탭 두 개가 서로의 세션을 지운 이야기. [다음 편: BeautyBoy 트러블슈팅 — 재고, 락, 그리고 동시성]에서 이어진다.
