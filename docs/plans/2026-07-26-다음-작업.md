## 1. 먼저 마감할 것 — 작고 확실하다

새 기능보다 이걸 먼저 한다. 이 프로젝트가 스스로 정한 최우선 가치가
**"완성도 있는 범위 + 설계 이유를 설명할 수 있는 것"**(`CLAUDE.md`)이고, 아래는 전부
**평가자·사용자에게 바로 보이는** 항목이면서 파일 1~2개로 끝난다.

### 1-1. `frontend/.env.example`의 토스 키 계열 불일치 ★ 최우선

**증상**: README를 그대로 따라 `.env.example`을 복사한 사람은 **결제가 안 된다.**

`frontend/.env.example`이 `VITE_TOSS_CLIENT_KEY=test_gck_docs_...`(**결제위젯** 계열)인데,
`frontend/src/features/payment/toss.ts:26-28`은 `tossPayments.payment({ customerKey })` +
`requestPayment(...)` — **결제창** 플로우다. 결제창은 `test_ck_` / `test_sk_` 쌍을 쓴다.
계열을 섞으면 결제창은 열리지만 **승인 단계에서 실패**한다.

→ `.env.example`의 값을 **결제창 계열 공개 테스트 클라이언트 키**로 바꾼다.
`README.md`의 "B-2. 백엔드 로컬 설정" 절에 이미 이 함정을 경고하는 인용문을 넣어뒀으니 문구는
그것과 맞춘다. **실제로 승인까지 통과한 키 쌍으로 확정할 것** — 미검증 값을 커밋하지 않는다.

### 1-2. 실제 토스 결제창 승인 1회 (사람이 해야 함, 아직 미수행)

**Wave 4 DoD의 마지막 미충족 항목이다.** Playwright E2E는 `e2e` 프로필의
`FakePaymentGateway`(`@Profile("e2e")`)로 돌기 때문에 이걸 대체하지 못한다.

절차는 `README.md`의 "B. 로컬 실행"을 따르되 **`e2e` 프로필이 아닌 기본/`local` 프로필**로
띄운다(`e2e`면 실제 토스 호출이 일어나지 않아 의미가 없다):

1. 백엔드에 실제 `TOSS_SECRET_KEY`(테스트 시크릿), 프론트 `frontend/.env.local`에 짝이 맞는
   `VITE_TOSS_CLIENT_KEY`
2. `dry@beautyboy.dev` / `seed1234!` 로그인 → `/routine` → 전체 담기 → 장바구니(98,150원)
   → 주문하기 → 결제하기
3. 토스 **테스트 카드**로 승인 → "주문이 완료되었습니다" + 주문번호·금액 확인
4. `/mypage/orders/{주문번호}`에서도 조회되는지 확인

**통과 기준**: 전 구간 에러 없이 이어지고 **결제 금액이 장바구니 합계와 일치**.
실패하면 주소창 쿼리스트링에 사유가 찍힌다(키 쌍 불일치면 여기서 드러난다).

### 1-3. `client.ts`의 409를 401과 구분하기

`frontend/src/api/client.ts:81-84`:

```ts
} catch (refreshError) {
  useAuthStore.getState().clear();
  return Promise.reject(refreshError);
}
```

원인이 무엇이든 **무조건 `clear()`** 한다. Task 4-16a가 새로 만든
`AUTH_REFRESH_CONFLICT`(409)는 "지금은 확인 못 했을 뿐 유효한 세션"인데 이 경로로 오면
세션이 파괴된다 — **4-16a가 `App.tsx`에서 없앤 바로 그 동작이 여기엔 그대로 남아 있다.**
(4-16a 당시 `client.ts`가 동결 계약이라 손대지 못했다. **이제 웨이브가 끝나 풀렸다.**)

→ `refreshError`가 axios 에러이고 `status === 401`일 때만 `clear()`한다.
`frontend/src/App.tsx`의 `isSessionGone()` 패턴과 동일하게 맞춘다.

**함께 볼 것**: in-flight 리프레시 캐시가 **두 벌**이다 — `frontend/src/api/auth.ts`의
`inFlightRefresh`와 `client.ts`의 `refreshPromise`가 서로 다른 promise를 들고 있어 두 경로가
동시에 리프레시를 쏘면 중복 제거가 안 된다(409를 받을 조건이 여기서 만들어진다). 한 벌로
합치는 것이 근본 해결이다.

**증상**: 여러 탭에서 동시에 하드 네비게이션하면 늦은 탭이 로그인 화면을 볼 수 있다(새로고침 1회로 복구).

### 1-4. 마이페이지 주문 목록에 주문번호 표시

`frontend/src/pages/mypage/MyOrders.tsx:34-84`가 날짜·대표상품명·금액만 보여주고 주문번호는
상세에만 있다. 재주문으로 세 값이 우연히 같은 건이 쌓이면 목록에서 구분이 불가능하다.

### 1-5. `/order/fail`을 `RequireAuth` 밖으로

`frontend/src/router.tsx:107-112`가 `order/fail`을 `RequireAuth`로 감싼다. API를 호출하지 않는
화면인데 리프레시가 실패하면 **결제 실패 사유 대신 `/login`으로 튕겨**, 사용자가 왜 결제가
안 됐는지 못 본다.

## 2. Wave 5 핵심 — 재고 차감과 동시성 ★★ [opus]

**가장 중요한 남은 작업이다.**

### 결함

`backend/src/main/java/com/beautyboy/order/OrderService.java:73-77`:

```java
// 재고는 검증만 한다. 차감은 Wave 3(오늘드림 store_stock 조건부 차감)의 몫이며,
// 여기서 깎으면 두 벌의 재고 개념이 생겨 정합성이 무너진다.
if (snapshot.stock() < item.quantity()) {
    throw new BusinessException(ErrorCode.ORDER_OUT_OF_STOCK);
}
```

주석은 "차감은 Wave 3의 몫"이라고 적었지만 **실제로 어디에도 구현되지 않았다.**
`goods_option.stock`을 감소시키는 코드가 프로젝트 전체에 없다(`grep`으로 확인).

**결과**:
- 재고 10개인 상품을 **100번 팔 수 있다.**
- 두 사람이 동시에 마지막 1개를 사면 **둘 다 성공한다.**
- Task 4-18이 `optionNo=null` 재고 검증 우회를 막았지만, 정작 그 게이트가 재고를 줄이지 않으니
  반쪽이다.

### 유력한 접근

**조건부 갱신의 영향 행 수로 성공/실패를 가른다:**

```sql
UPDATE goods_option SET stock = stock - :qty WHERE id = :id AND stock >= :qty
```

영향 행이 1이면 확보, 0이면 품절. **Task 4-16a가 리프레시 토큰에 쓴 것과 정확히 같은 패턴이고,
그 태스크에서 이미 검증된 기법이다**(낙관적 락 예외에 의존하지 말 것 — H2와 InnoDB에서 예외
타입이 달라 실 MySQL에서 조용히 깨진다. 이 프로젝트엔 H2가 실 MySQL 문제를 가린 이력이 있다).

### 판단해야 할 지점 (계획서에 못 박을 것)

- **차감 시점**: 주문 생성 시점인가, 결제 승인 시점인가. 주문 생성에서 깎으면 결제를 안 한
  주문이 재고를 잠그고, 승인에서 깎으면 승인은 됐는데 재고가 없는 상황이 생긴다.
- **실패 시 복원**: 결제 실패·취소 시 어떻게 되돌리는가. 복원 누락이 재고 유실을 만든다.
- **부분 실패**: 여러 상품 중 하나만 품절이면 이미 깎은 것들을 어떻게 처리하는가.
- **오늘드림의 `store_stock`과의 관계**: 위 주석이 경고한 "두 벌의 재고 개념"을 어떻게 피하는가.

**`CLAUDE.md`의 모델 배분에서 이 영역(돈·재고 정합성, 오늘드림 재고 차감)은 opus 예외다.**

### DoD 후보

동시 주문 2건이 마지막 재고 1개를 다툴 때 **정확히 한쪽만 성공**하고 다른 쪽은
`ORDER_OUT_OF_STOCK`, 500이 나지 않으며, 재고가 음수가 되지 않는다.
**동시성은 H2와 InnoDB의 락 동작이 다르므로 `integrationTest`(실 MySQL)를 신뢰 근거로 삼는다.**
`AuthRefreshConcurrencyScenario`(추상 클래스 + H2/실MySQL 서브클래스 2벌)가 확립된 패턴이니
그대로 따라 쓰면 된다.

## 7. 정리해야 할 것

- **`.claude/worktrees/BeautyBoy-w4`** worktree가 아직 남아 있다. Wave 4는 머지가 끝났으니 지워도
  된다: `git worktree remove .claude/worktrees/BeautyBoy-w4 && git worktree prune`
  (그 안의 `.superpowers/sdd/`에 Wave 4 태스크별 리포트·원장이 있는데 **gitignore라 커밋되지
  않았다** — worktree를 지우면 사라진다. 필요하면 먼저 옮겨둔다.)
- 수동 테스트용으로 띄워둔 개발 서버·컨테이너가 남아 있을 수 있다:
  `pkill -f bootRun; pkill -f vite; docker rm -f bb-dev-mysql`
- `frontend/.env.local`은 gitignore 대상이라 커밋되지 않는다(로컬 토스 키 주입용).

## 8. 잊지 말 것 — Wave 4에서 배운 것

- **화면을 만드는 작업은 렌더 결과를 눈으로 봐야 완료다.** Wave 4에서 유닛·통합·E2E가 전부 녹색인
  상태로 (a) 헤더 장바구니 배지가 하드코딩 `0`이고 `/cart` 링크가 죽어 있었고, (b) 상세 페이지에서
  담아도 배지가 새로고침 전까지 안 올라갔다. **둘 다 사람이 브라우저를 열고 나서야 발견됐다.**
- **화면 이상은 추정하지 말고 코드로 찍는다.** (a)를 "스크린샷 타이밍 아티팩트"로 오진한 사례가 있다.
- **E2E가 지나가는 경로만 보호된다.** (b)는 E2E가 루틴 전체담기 경로만 지나가고 상세 담기 경로를
  지나가지 않아 잡히지 않았다.
- **동시성은 실 MySQL에서 검증한다.** H2가 실 MySQL 문제를 가린 이력이 있다.
- 커밋 메시지·문서·주석은 한국어. 커밋은 태스크 단위로 원자적으로.
