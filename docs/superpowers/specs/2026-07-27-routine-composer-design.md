## 0. 왜 v2인가 — v1의 실측된 한계

v1을 가동해 보고 실측으로 확인한 문제 4개가 출발점이다. 전부 이 문서의 §로 해소된다.

| # | 실측된 문제 | 원인 | 해소 |
|---|---|---|---|
| 1 | 개인화 해상도가 "칸(단계×태그)"에서 멈춤 — 같은 칸이면 전원이 같은 상품 | 후보 조회가 `sort=popular` 고정, 개인화는 칸 선택까지만 | §2 점수 공식이 상품 단위로 순위를 매김 |
| 2 | 조회 1점이 담기 30점을 이김 | `priority`가 1차 정렬키, 점수는 tie-break | §2 공식으로 흡수 — priority 폐기 |
| 3 | 행동 5건 넘는 순간 선택지 18→9로 감소 | 티어2가 `concernRules`를 통째로 미사용 | §2 티어 사다리 폐지 — 신호를 한 공식에 합산 |
| 4 | 메인은 pairwise 궁합 검증 불가 ("앵커 상품이 없다") | 칸 선택 구조라 기준 상품이 없음 | §3 체인 — 앞 단계 픽이 앵커가 됨 |

## 1. 한 줄 요약

메인이 "칸을 골라 인기순을 보여주는" 화면에서 **"이 사용자의 5단계 루틴 한 벌을 조합해 바로
사게 하는"** 화면이 된다. 모든 신호(프로필 고민·사용감·조회·찜·담기)를 **점수 공식 하나**로
합산해 단계마다 대표 픽 1개 + 대안 3개를 뽑고, 앞 단계 픽이 다음 단계에 **전이 규칙 보너스와
궁합 게이트**로 개입한다. 계산은 전부 기기에서 한다(v1 §9의 서버 비용 원칙 유지).

## 2. 점수 공식 — 티어 사다리를 폐지한다

단계마다 후보 풀(그 카테고리 인기순 12개, 태그 필터 없음)을 받아 **모든 후보**에 적용한다:

```
score(상품 p, 단계 s) =
    2.0 × concernMatch(p)      // min(|p.tags ∩ 고민|, 2)
  + 1.5 × behaviorAffinity(p)  // Σ_{t∈p.tags} A(s.cat3, t) 를 후보 중 최대값으로 나눔 (0~1)
  + 1.0 × flowBonus(p)         // 이전 단계 픽에서 발동한 전이 규칙의 to_tag ∈ p.tags 면 1
  + 0.5 × textureMatch(p)      // min(|p.tags ∩ 선호 사용감|, 1)
  + 0.3 × popularityPrior(p)   // (12 − 서버 순위) / 12
  단, 이전 단계 픽과 CONFLICT 이면 후보에서 제거 (§3 게이트)
```

- `A(cat3, tag)`는 v1 §6.1의 `aggregate()` 그대로 — **조회 1 · 찜 2 · 담기 3이 여기서
  연속적으로 살아남는다.** 문제 #2의 해소 지점이다.
- **티어 분기가 없다.** 신호가 없는 항은 0이 될 뿐이다: 콜드스타트는 `popularityPrior`만 남아
  자연히 인기순(현재 기준선)으로 수렴하고, 프로필만 있으면 `concernMatch`가, 행동이 쌓이면
  `behaviorAffinity`가 점진적으로 얹힌다. 문제 #3의 "5건째에 화면이 널뛰는" 불연속이 사라진다.

### 2.1 가중치의 근거 (매직넘버 — 바꿀 때 이 표를 먼저 고친다)

| 항 | 가중치 | 왜 이 크기인가 |
|---|---|---|
| concernMatch | 2.0 | **직접 선언**한 취향이 최상위. 고민 1개 일치(2.0)가 사용감+인기(0.8) 합을 항상 이긴다 |
| behaviorAffinity | 1.5 | 암묵 신호는 선언보다 한 단계 아래. 단 최대치(1.5)+flowBonus(1.0)=2.5로, **지속된 행동 + 체인 정합이 고민 1개를 뒤집을 수 있다** — 선언이 낡았을 때 행동이 이기는 통로를 남긴다 |
| flowBonus | 1.0 | 맥락(앞 단계와의 이어짐)은 개인 신호보다 아래, 취향 미세조정보다 위 |
| textureMatch | 0.5 | 사용감은 "무엇을"이 아니라 "어떤 느낌으로"의 축 — 동급 후보 사이만 가른다 |
| popularityPrior | 0.3 | 신호 없을 때의 하한. 어떤 개인 신호 하나에도 뒤집히는 크기여야 한다 |
| 상한 min(·,2), min(·,1) | — | V83 이후 상품당 태그 최대 3개 — 태그 다수 보유가 점수를 지배하지 못하게 캡 |

- 동점은 `popularityPrior` → `goodsNo` 순으로 깨서 **완전 결정적**으로 만든다(테스트 가능).
- `priority` 컬럼은 목표 선택에 더 이상 쓰지 않는다. BUFFER 우대는 flowBonus가 규칙 매칭
  단계에서 계승한다(§3.2).

## 3. 체인 — 앞 단계의 픽이 다음 단계를 끌고 간다

### 3.1 조합 순서

```
STEP 1 후보 12개 → 공식 적용 → 픽 확정
STEP 2 후보 12개 → 픽(1)과 CONFLICT 인 후보 제거          ← 궁합 게이트 (§3.3)
                 → 픽(1) 태그로 발동한 전이 규칙의 to_tag 에 flowBonus  ← 흐름 (§3.2)
                 → 공식 적용 → 픽 확정
STEP 3~5 동일하게 반복
```

"각질 클렌저를 많이 봄"의 경로가 두 겹이 된다: (a) 행동 친화도가 STEP 1에서 각질 클렌저를
픽으로 밀고 → (b) 그 픽이 전이 규칙(`C002001×exfoliate → C001001×soothe`)을 발동해 STEP 2의
진정 토너에 보너스를 준다. **행동이 같은 단계에는 직접, 다음 단계에는 픽을 통해 전이적으로
영향을 준다** — 요구사항 "이전 step 행동이 다음 step에 영향"의 구조적 답이다.

### 3.2 전이 규칙 매칭 (flowRules 재사용)

- 이전 픽의 (중분류, 태그들)에 `from_category_code` 접두사 일치 + (`from_tag_slug` null 또는
  픽 태그에 포함)인 규칙 중, **BUFFER > NEXT_STEP 순, 같으면 낮은 priority** 로 1개 선택.
  (priority의 남은 역할은 이 규칙 내부 선택뿐이다 — 단계 간 경쟁에는 쓰지 않는다.)
- 선택된 규칙의 `to_category_code`가 이번 단계면: `to_tag_slug ∈ p.tags`인 후보에 flowBonus 1,
  섹션에 그 규칙의 `reason` 문장 표시. `to_tag_slug`가 null이면 보너스 없이 문장만 표시.
- 규칙이 안 걸리면 `concernRules`에서 이 단계를 겨냥한 고민 규칙(사용자 고민 순 → priority 순)의
  reason을 쓴다. 그것도 없으면 **문장 없이 근거 칩만**(§5) — 문구를 코드에 만들지 않는다는
  원칙은 그대로다(reason의 출처는 두 규칙 테이블뿐).

### 3.3 궁합 게이트 — pairwise API 신설 (서버 작업의 전부)

```
GET /api/v1/compat/verdicts?base={goodsNo}&candidates={csv, 최대 12}
→ ApiResponse<Map<Long, String>>   // 후보별 최악 verdict
```

- `compat` 패키지 컨트롤러 신설, 기존 `CompatQueryService.worstVerdicts(base, candidates)`
  위임 — **서비스 로직 변경 없음, 마이그레이션 없음.** `SecurityConfig` permitAll 1줄.
- 클라이언트는 단계 경계마다 1회(총 4회) 호출해 `CONFLICT` 후보를 제거한다. 대안 3개도 같은
  풀에서 나오므로 함께 걸러진다.
- v1 §10의 명시된 한계 *"메인은 규칙 수준 안전까지만 — 앵커 상품이 없어 pairwise가 성립하지
  않는다"* 는 **이 설계로 해소된다**(픽이 앵커다). 문제 #4.
- 호출이 실패하면 게이트 없이 진행한다(전이 규칙 자체가 궁합의 하위 호환이라 규칙 수준
  안전은 유지) — 궁합 확인 실패로 메인이 멈추면 안 된다.

### 3.4 렌더 순서

체인은 순차지만 화면은 **위에서부터 점진 렌더**한다 — STEP 1이 먼저 확정·렌더되고 STEP 2가
따라온다. 스크롤 방향과 확정 순서가 같아 사용자는 지연을 체감하지 못한다. 각 섹션이 자기
데이터를 가져오는 기존 구조에 "이전 픽 확정 대기"만 추가된다(React Query 의존 쿼리).

## 4. 화면 — 보이는 대로 산다

### 4.1 대표 픽 카드 (섹션당 1개, 그리드 첫 자리를 대체·확장)

- 픽 상품을 큰 카드로: 썸네일, 태그 칩(기존 팔레트), **근거**(§5), 가격, **[바로 담기]** 버튼.
- **대안 3개**는 점수 2~4위를 기존 `GoodsCard` 그대로 나란히.
- 콜드스타트(신호 전무)면 픽 카드도 "인기 1위"로 동작하되 근거 문장 없이 — 화면 구조는
  동일하고 내용만 기준선이다. v1의 "개인화 섹션 최대 2개" 규칙은 **이 설계에서 폐기한다** —
  그 규칙은 "기준선 화면의 일부 교체" 패러다임의 것이었고, v2의 패러다임은 "루틴 한 벌 조합"
  이라 5단계 전부가 조합 대상이다.

### 4.2 바로 담기 — 클릭 1회

- 클릭 → 상세 조회(캐시되면 0회) → **재고 있는 첫 옵션**으로 장바구니 POST → 토스트
  "담았어요 — 옵션 변경은 장바구니에서". 재고 전무면 버튼 비활성 + "일시품절".
- 가격·재고 검증은 어차피 서버(cart 도메인)가 한다 — "돈과 재고는 서버" 원칙 그대로.

### 4.3 루틴 전체 담기

- STEP 05 아래에 **"오늘의 루틴 5개 담기"** CTA 1개. 5개 픽을 순차 담고 결과 토스트
  ("5개 담았어요 / 1개는 품절로 제외"). 실패 항목은 건너뛰고 보고 — 전부 롤백하지 않는다
  (장바구니는 편집 가능한 중간 상태다).
- 새 시각 컴포넌트(픽 카드·CTA)는 **DESIGN.md에 사양을 먼저 추가**하고 토큰만 참조한다.

## 5. 근거 표시 — 설명 가능성

픽 카드에 신호별 근거를 계층적으로:

1. **reason 문장** — 발동한 규칙의 `reason`(§3.2). DB가 유일한 출처.
2. **근거 칩** — 점수에 실제 기여한 태그만 강조: 고민 일치 태그(팔레트 색), 행동 친화 태그.
   칩은 데이터(태그)지 문구가 아니므로 하드코딩 원칙과 충돌하지 않는다.

## 6. 성과 측정 — 시뮬레이션 테스트 (서사의 핵심)

조합기는 순수 함수이므로 **실데이터 스냅샷 픽스처**(V83 적용 후 190개 상품의 goodsNo·카테고리·
태그·인기순위를 JSON으로 추출해 커밋)에 대해 CI에서 재현 가능한 수치를 뽑는다:

- **차별화**: 서로 다른 프로필·행동 조합 N종(≥20)의 메인 구성(단계별 상위 4) 간 평균 자카드
  유사도. **기준선(전원 인기순) = 1.0 대비 유의미하게 감소**를 단언하고 실측값 출력.
- **개인화 커버리지**: 신호가 있는 사용자에서 픽이 기준선(인기 1위)과 달라진 단계 비율.
- **연속성**: 행동 이벤트를 1개씩 늘려가며 구성 변화가 **단조·점진적**(5건째 급변 없음)임을 단언
  — 문제 #3의 회귀 테스트.
- **강도 반영**: 같은 상품 담기 횟수를 늘리면 관련 태그 후보의 순위가 올라감 — 문제 #2의 회귀 테스트.
- **궁합 0건**: CONFLICT 픽스처로 체인 결과에 충돌 쌍이 없음을 단언.

이 수치들이 포트폴리오 문장이 된다: *"태그 희석(67%)·정렬 편향·티어 불연속을 실측→수정하고,
190개 실데이터 시뮬레이션에서 사용자 간 구성 유사도 X→Y, 커버리지 Z%를 검증했다."*

## 7. 무엇이 대체되고 무엇이 남는가

| 기존 | v2에서 |
|---|---|
| `match.ts`의 `matchByBehavior`/`matchByProfile`/티어 분기 | **`composer.ts`로 대체** (점수 공식 + 체인) |
| `RoutineSection`의 부분 채움 | **자연 소멸** — 풀이 태그 필터 없는 12개라 항상 가득. 태그는 필터가 아니라 점수 항이 됐다 |
| `rankByTexture` | 공식의 textureMatch 항으로 흡수 |
| v1 §6.1 행동 로그, §5 규칙 배포 API(ETag), §4 프로필 태그, V83 태그 정리 | **그대로 사용** — 이 설계의 입력이다 |
| 개인화 섹션 최대 2개 | 폐기 (§4.1) |
| "메인은 규칙 수준 안전만" 한계 | 해소 — pairwise 게이트 (§3.3) |

## 8. 검증 (DoD)

- `composer.ts` 유닛: 공식 각 항의 캡·정규화·동점 결정성 / 체인 flowBonus 발동·미발동 /
  게이트 제거 / BUFFER > NEXT_STEP 규칙 선택 / reason 폴백 사다리(§3.2).
- §6 시뮬레이션 전량 + 실측값 출력.
- compat API IT: 200 응답 / CONFLICT 픽스처 verdict / permitAll.
- 화면: 픽 카드·바로 담기·전체 담기 렌더 테스트(MSW) + **스크린샷** —
  서로 다른 두 계정의 메인이 눈에 보이게 다른 것, 바로 담기 토스트.
- 실기동 curl 스모크(체인 4회 호출 + verdicts 응답).

## 9. 한계 (명시)

- 후보 풀이 단계당 인기순 12개라 **12위 밖 상품은 개인화로도 못 올라온다** — 풀 크기는
  페이로드와의 트레이드오프이고, 값은 상수로 두어 조정 가능하게 한다.
- 가중치는 휴리스틱이다. A/B 테스트 인프라가 없으므로 "정확도"를 주장하지 않고, §6처럼
  **구조적 성질**(차별화·연속성·강도 반영·안전)만 검증한다 — v1 §9 검증 철학의 계승.
- 기기 간 행동 비일관은 v1 §10 그대로 남는다.

## 10. 실행 구조 (구현 계획서에서 확정)

터미널 3개: ① composer 순수 함수 + 시뮬레이션(프론트, 서버 의존 없음) ② compat verdicts API
