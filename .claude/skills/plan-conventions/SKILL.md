# 설계·구현 계획 작성 규칙 (매 계획 공통)

설계 문서나 구현 계획을 만들 때 별도 지시 없이 항상 아래 구조로 작성한다.

1. 구현·테스트 작업은 서브에이전트가 실행하고, 메인 세션은 오케스트레이터(스폰·리뷰·머지 게이트)로 둔다. (모델 배분은 위 표 따름)
2. 병렬 가능한 태스크는 웨이브/의존성을 분석해 **터미널 분할**을 계획서에 명시한다. (터미널 1개 = worktree 1개 = 브랜치 1개)
3. 터미널을 분할하는 경우, **각 터미널에서 그대로 붙여넣어 쓸 실행 프롬프트**를 계획서 안에 함께 생성한다.

   **사람은 프로젝트 루트에서 터미널을 열고 프롬프트를 붙여넣기만 한다.** git 명령을 손으로 치지 않는다.
   따라서 **worktree 생성·진입·기점 검증 지시를 프롬프트 본문 안에 넣는다** — 사람이 실행할 별도
   bash 블록으로 빼지 않는다. 빼두면 프롬프트만 복사해 붙이는 순간 진입 없이 시작하게 되고,
   터미널마다 브랜치를 즉흥으로 만들어 기점이 어긋난다.

   프롬프트는 **[1단계 작업 공간 → 2단계 실행]** 두 단으로 쓰고, 1단계에 아래를 담는다.

   ```
   [1단계 — 작업 공간 만들기] 다른 무엇보다 먼저 이것부터 해라.
     git worktree add .claude/worktrees/뷰티보이-<세트> -b <브랜치명>
   를 실행한 뒤 EnterWorktree 도구에 path로 그 경로를 넘겨 세션을 그 안으로 옮겨라.
   진입 후 아래를 확인하고, 하나라도 어긋나면 중단하고 보고해라:
     - pwd가 해당 worktree인지
     - git log --oneline -1 이 루트에서 본 기점 커밋과 같은지
     - 계획서와 참조 문서(DESIGN.md 등)가 실제로 존재하는지
     - git status가 깨끗한지
   [2단계 — 실행] (이하 태스크 지시)
   ```

   - **worktree 위치는 반드시 `.claude/worktrees/` 아래다.** `EnterWorktree`는 이 저장소의
     `.claude/worktrees/` 밖에 있는 worktree로는 세션을 옮기지 못한다(형제 디렉토리 `../…`로
     만들면 "is not under … .claude/worktrees" 오류로 거부된다). 이 경로는 gitignore에 이미
     들어 있다(`.claude/worktrees/`). 잘못된 위치에 이미 만들었다면 지우지 말고
     `git worktree move <기존경로> .claude/worktrees/<이름>` 후 다시 진입한다.
   - **`EnterWorktree`를 `name`으로 새로 만들게 하지 않는다.** 기본 설정(`worktree.baseRef: fresh`)이
     로컬 HEAD가 아니라 `origin/<기본브랜치>`에서 브랜치를 딴다. 푸시가 밀려 있으면 계획서도 참조
     문서도 없는 worktree가 생긴다. 항상 `git worktree add`(로컬 HEAD 기준) 후 `path`로 진입시킨다.
   - **기점 검증은 프롬프트가 시킨다.** 계획서·참조 문서가 untracked면 새 worktree에 딸려가지 않으므로,
     터미널을 열기 전에 루트에서 커밋돼 있어야 한다. 계획서 커밋이 특정 feature 브랜치에만 들어가 있으면
     다른 터미널이 못 보므로, 해당 커밋에서 브랜치를 따거나 cherry-pick 한다.
   - 계획서에는 사람 몫으로 **사전 조건 확인 2줄**(`git log --oneline -1`로 기점 확인, `git status`가
     깨끗한지)만 남긴다.

4. **코드를 어디까지 적는가 — 판단이 있는 곳만 전량으로 적는다.**

   이 항목은 `superpowers:writing-plans`의 "모든 스텝에 완전한 코드" 요구를 **덮어쓴다.**
   기준은 분량이 아니라 **틀렸을 때 조용히 사고가 나는가**다. 컴파일이 막아주는 것은 계획서가 막을 필요가 없다.

   **완전한 코드로 적는다:**
   - **공유 계약** — Flyway DDL, 공통 응답/에러 타입, 도메인 간 서비스 인터페이스 시그니처.
     여러 터미널이 이것에 동시에 의존하므로 한 글자만 어긋나도 전부 깨진다.
   - **판단이 갈리는 로직** — 동시성(락·조건부 갱신), 돈·재고 정합성, 상태 전이 조건, 규칙 충돌 해석.
     (모델 배분 예외 3종과 같은 영역이다.)
   - **매직넘버와 그 근거** — 가중치·임계값·집계 창. 값만 적고 왜 그 값인지 안 적으면 나중에 아무도 못 고친다.
   - **자명하지 않은 쿼리** — 네이티브 SQL, 성능 의도가 있는 조회.
   - **테스트 케이스 이름과 단언 전량** — 무엇이 통과 조건인지가 곧 사양이다. 여기는 줄이지 않는다.

   **시그니처 + 사양 문장으로 충분하다:**
   - 엔티티의 getter·생성자, 순수 DTO/record
   - 위임만 하는 컨트롤러 핸들러
   - Spring Data 메서드명으로 끝나는 리포지토리
   - 플레이스홀더 에셋(SVG 등) — 규격과 파일명만 적고 내용은 맡긴다

   단 **"적절히 처리"·"위와 유사"·TBD는 여전히 금지**다. 사양 문장은 **검증 가능**해야 한다 —
   "무엇이 참이면 통과인지"가 적혀 있지 않으면 그것은 사양이 아니라 미룬 결정이고,
   그 해석 비용이 병렬 터미널 수만큼 곱해진다.
