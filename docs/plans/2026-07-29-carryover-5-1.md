## 2. 설계 결정

### 결정 1 — clamp 공용화는 DRY가 아니라 **500 버그 수정**이다

이 항목을 "급하지 않다"고 미뤄 뒀는데, 실제로 돌려 보면 급하다. 실행 중인 백엔드에 대고:

```
GET /api/v1/goods?size=0    → 200, content:[], totalPages:0   (의미 없는 빈 페이지)
GET /api/v1/goods?size=-1   → 500 INTERNAL_SERVER_ERROR
GET /api/v1/goods?page=-1   → 500 INTERNAL_SERVER_ERROR
```

원인은 5곳의 clamp가 **서로 다르기 때문**이다.

| 위치 | 현재 코드 | 하한 |
|---|---|---|
| `OrderService:106-107` | `max(page,0)` + `min(max(size,1),100)` | 있음 |
| `QnaService:71` | `min(max(size,1),100)` | size만 있음 |
| `GoodsController:44` | `min(size,100)` | **없음** |
| `AdminGoodsController:38` | `min(size,100)` | **없음** |
| `SearchController:47` | `min(size,100)` | **없음** |

하한이 없는 셋은 음수가 `PageRequest.of`까지 그대로 흘러가 `IllegalArgumentException` → 500이
된다. 즉 "같은 값을 쓰는가"는 맞췄지만 **같은 일을 하지는 않았다.** 공용화하면 이 세 곳이
`OrderService`의 이미 옳은 동작을 물려받는다.

`common`을 여는 것은 이 때문이다. 다만 **추가만 한다** — 기존 타입은 손대지 않으므로 다른
계약이 깨질 표면이 없다.

```java
package com.beautyboy.common;

/**
 * 페이지 파라미터 정규화. 손님이 보낸 page·size를 리포지토리에 넘기기 전에 안전한 범위로 조인다.
 *
 * <p>이 클래스가 생기기 전에는 같은 상한 100이 5곳에 복붙돼 있었고 하한 처리가 서로 달랐다 —
 * {@code GoodsController}·{@code AdminGoodsController}·{@code SearchController}에는 하한이 없어
 * {@code ?size=-1}·{@code ?page=-1}이 {@code PageRequest.of}에서 터져 500으로 샜다.
 * 판정 주체를 하나로 모아 그 클래스의 버그를 통째로 없앤다.
 */
public final class PageRequests {

    /**
     * 한 번에 내려주는 최대 행 수. 목록 화면 중 가장 큰 것이 admin 상품 목록(기본 20)이고,
     * 100이면 그 5배다 — 운영상 필요한 범위를 덮으면서 응답 직렬화가 폭주하지 않는 선.
     */
    public static final int MAX_PAGE_SIZE = 100;

    private PageRequests() {
    }

    /**
     * size를 [1, MAX_PAGE_SIZE]로 조인다. 0과 음수는 1로 올린다 —
     * Spring Data의 {@code PageRequest.of}가 1 미만을 거부하기 때문이다.
     */
    public static int clampSize(int size) {
        return Math.min(Math.max(size, 1), MAX_PAGE_SIZE);
    }

    /** page 음수를 0으로 내린다. {@code PageRequest.of}가 음수를 거부한다. */
    public static int clampPage(int page) {
        return Math.max(page, 0);
    }
}
```

**동작이 바뀌는 지점을 명시한다** — 조용히 넘어가면 안 되는 곳이다.

| 요청 | 변경 전 | 변경 후 |
|---|---|---|
| `goods?size=0` | 200, 빈 페이지 `totalPages:0` | 200, **1건**짜리 페이지 |
| `goods?size=-1` | **500** | 200, 1건짜리 페이지 |
| `goods?page=-1` | **500** | 200, 0페이지 |
| `goods?size=1000` | 200, 100건 (변화 없음) | 200, 100건 |
| `orders?*` | (이미 옳음) | 변화 없음 |

`size=0`을 400으로 막지 않는 이유: 나머지 네 곳이 이미 "조여서 처리"이고, 여기만 400을 내면
같은 파라미터가 엔드포인트마다 다르게 반응한다. **판정 주체를 하나로 모으는 게 이 태스크의
목적**이므로 동작도 하나로 모은다.

### 결정 2 — admin Bean Validation은 §0-4 결정 3의 경계를 그대로 상속한다

§0-4가 손님 경로에 그은 선을 admin에도 똑같이 긋는다. **재해석하지 않는다.**

**애노테이션이 맡는 것 = 지금 아무도 안 막아 NPE·DB 예외(500)로 새는 것** → `null`, 공백,
컬럼 길이 초과.

**서비스가 계속 판정하는 것 = 이미 도메인 ErrorCode를 가진 값** → 아래에는 **붙이지 않는다.**

| 값 | 판정 주체 | 코드 |
|---|---|---|
| `AdminGoodsSaveRequest.categoryCode`의 **유효성** | `AdminGoodsService:132` | `GOODS_CATEGORY_INVALID` |
| `AdminGoodsSaveRequest.listPrice`/`salePrice`의 **관계·범위** | `AdminGoodsService:138` | `GOODS_PRICE_INVALID` |
| `RoutineStepGoodsRequest.goodsNos`의 **존재 여부** | `AdminRoutineService:51` | `ROUTINE_STEP_GOODS_INVALID` |

`categoryCode`에는 `@NotBlank`와 `@Size(max = 12)`만 붙인다 — **비어 있음**과 **길이**는 구조적
결손이고, **그 코드가 실재하는 카테고리인가**는 서비스 몫이다. 두 관심사를 한 필드에서 나눠
갖는 것이 이 경계의 요점이다.

가격에는 `@PositiveOrZero`조차 붙이지 않는다. `GOODS_PRICE_INVALID`가 이미 판정하고 있고,
애노테이션을 얹으면 그 코드가 조용히 `INVALID_INPUT`으로 바뀌어 admin 화면의 분기가 깨진다.

`goodsNos`는 `@NotNull`만 붙인다. **빈 배열은 유효한 요청**이다(그 단계의 추천을 비운다는 뜻).
`null`일 때만 `goodsQueryService.findListItems(null, ...)`에서 NPE로 샌다.

컬럼 길이는 **엔티티가 진실**이다(`Goods.java:46-68`, `Qna.java:38`).

| 필드 | 애노테이션 | 근거 |
|---|---|---|
| `AdminGoodsSaveRequest.brandId` | `@NotNull` | 없으면 FK NPE |
| `.categoryCode` | `@NotBlank` `@Size(max = 12)` | `length = 12` |
| `.name` | `@NotBlank` `@Size(max = 200)` | `length = 200` |
| `.summary` | `@Size(max = 300)` | `length = 300`, nullable |
| `.thumbnailUrl` | `@NotBlank` `@Size(max = 300)` | `nullable = false, length = 300` |
| `.status` | `@Size(max = 20)` | `length = 20`, 등록 시 무시되는 값이라 `@NotBlank` 안 붙임 |
| `AdminQnaAnswerRequest.answer` | `@NotBlank` `@Size(max = 2000)` | `Qna.answer length = 2000`, 서비스에 공백 검사 없음 |
| `RoutineStepGoodsRequest.goodsNos` | `@NotNull` | null이면 NPE |

### 결정 3 — queryKey 팩토리는 **키를 만드는 유일한 곳**이 된다

`['cart']`가 8개 파일에 하드코딩돼 있고 정합성을 주석으로 지킨다(`Header.tsx:46-47`의
"Cart.tsx:27과 반드시 같은 ['cart']를 쓴다"). 주석이 지키는 규칙은 주석을 안 읽은 사람이 깬다.

**곁들여 고칠 실제 버그가 하나 있다.**

```ts
// Cart.tsx:37   — 정렬·중복제거 없음
queryKey: ['compat', goodsNos.join(',')],
// Routine.tsx:86 — 역시 없음. 주석은 "Cart와 같은 패턴"이라 적혀 있다
queryKey: ['compat', selectedGoodsNos.join(',')],
```

둘 다 정렬을 안 하므로 **같은 상품 조합도 선택 순서가 다르면 다른 캐시 엔트리**가 된다.
루틴에서 1→2를 고르든 2→1을 고르든 궁합 결과는 같은데 서버를 두 번 부른다. 팩토리가
정규화를 한 곳에서 하면 이 클래스가 통째로 사라진다.

```ts
// src/api/queryKeys.ts
/**
 * react-query 키를 만드는 유일한 곳. 화면이 키 배열을 직접 적지 않는다.
 *
 * 이전에는 ['cart']가 8개 파일에 하드코딩돼 있었고 "Cart.tsx와 같은 키를 써라"라는 주석으로
 * 정합성을 지켰다. 주석은 안 읽은 사람이 깨므로, 무효화하는 쪽과 조회하는 쪽이 같은 함수를
 * 부르게 해서 오타 클래스를 구조적으로 없앤다.
 */
export const queryKeys = {
  cart: () => ['cart'] as const,
  wishlist: () => ['wishlist'] as const,

  /**
   * 성분 궁합. 상품 번호 집합이 같으면 **고른 순서가 달라도 같은 캐시 엔트리**여야 한다 —
   * 궁합 판정은 조합의 함수이지 순서의 함수가 아니다. 중복제거 후 정렬해서 그 성질을 키에 넣는다.
   * (이전 Cart.tsx·Routine.tsx는 goodsNos.join(',')을 그대로 써서 1→2와 2→1이 서로 다른
   *  엔트리가 됐고, 같은 조합에 대해 서버를 두 번 불렀다.)
   */
  compat: (goodsNos: readonly number[]) =>
    ['compat', [...new Set(goodsNos)].sort((a, b) => a - b).join(',')] as const,
} as const;
```

정렬은 **숫자 비교자로** 한다. `.sort()` 기본은 문자열 비교라 `[2, 10]`이 `10,2`가 되어
같은 조합이 자릿수에 따라 갈린다.

이 태스크의 범위는 **`cart` · `wishlist` · `compat` 셋뿐**이다. 다른 키(`goods`, `ranking`,
`search` …)는 하드코딩이 한 곳뿐이라 팩토리가 얻는 게 없다. 전부 옮기려다 태스크가 부풀지 않게
여기서 자른다.

### 결정 4 — QueryClient 기본값: `staleTime`을 데이터의 변화 속도에 맞춘다

`App.tsx:9`가 `new QueryClient()` 그대로라 모든 쿼리가 `staleTime: 0` + `refetchOnWindowFocus:
true`다. 탭을 돌아올 때마다 랭킹·검색·상세는 물론 준정적 데이터까지 전부 다시 요청한다.

값과 근거를 못 박는다. **숫자만 적고 왜인지 안 적으면 나중에 아무도 못 고친다.**

```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      /**
       * 60초. 이 앱에서 가장 빨리 변하는 조회 데이터가 랭킹(집계 주기 분 단위)과
       * 재고 표시이고, 그보다 짧게 잡을 이유가 없다. 60초면 한 화면 안에서 오가는 동안
       * 재요청이 없고, 탭을 오래 비웠다 오면 다시 받는다.
       */
      staleTime: 60_000,
      /**
       * 5분. 화면을 떠나도 캐시를 이 시간만큼 들고 있어 뒤로가기가 즉시 그려진다.
       * staleTime보다 길어야 의미가 있다(짧으면 신선한 데이터를 버리게 된다).
       */
      gcTime: 5 * 60_000,
      /**
       * 끈다. 탭 전환은 "데이터가 낡았다"는 신호가 아니다 — 여기가 켜져 있어서
       * 알트탭 한 번에 화면 전체가 재요청을 걸었다. 신선도는 staleTime이 책임진다.
       */
      refetchOnWindowFocus: false,
      /**
       * 1회. 기본값 3회는 백엔드가 죽었을 때 오류 화면이 뜨기까지 손님을 오래 기다리게 한다.
       * 일시적 네트워크 실패는 1회 재시도로 대부분 걷히고, 진짜 장애는 빨리 드러나야 한다.
       */
      retry: 1,
    },
    mutations: {
      /** 재시도하지 않는다. 담기·주문·결제는 중복 실행이 곧 사고다. */
      retry: 0,
    },
  },
});
```

**돈이 걸린 쿼리에 이 기본값이 새면 안 된다.** 장바구니·주문서 금액은 `staleTime: 0`을
호출부에서 명시적으로 덮어쓴다 — 기본값이 "60초 동안 옛 가격을 보여줘도 된다"고 말하게 두면
CLAUDE.md의 "돈과 재고는 서버" 원칙과 어긋난다. 대상은 Task 2-3 Step 3에 열거한다.

### 결정 5 — 폰트는 **동적 서브셋 CDN**으로 로드하고, Inter도 같이 고친다

§5-1은 Pretendard만 적었지만 실제로는 **`--font-body`의 앞 두 폰트가 모두 미로드**다.
`index.html`에 `<link>`가 없고 `index.css`에 `@font-face`도 없다.

```css
/* index.css:82 — 선언은 있는데 실물이 없다 */
--font-body: Inter, 'Pretendard Variable', Pretendard, -apple-system, ...
```

즉 지금 화면에 그려지는 건 macOS의 `-apple-system`이고, Windows/Android에서는 `Malgun
Gothic`이나 `system-ui`다. **`DESIGN.md`가 정한 타이포가 어느 기기에서도 렌더된 적이 없다.**
포트폴리오를 남의 기기에서 열 때 바로 드러난다.

**동적 서브셋 CDN을 쓴다.**

```html
<link rel="preconnect" href="https://cdn.jsdelivr.net" crossorigin />
<link rel="stylesheet" as="style" crossorigin
      href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css" />
```

근거와 버린 대안:

- **왜 CDN인가** — Pretendard Variable 원본 woff2는 1.2MB급이라 셀프호스팅하면 첫 화면을
  그만큼 늦춘다. 동적 서브셋은 `unicode-range`로 쪼갠 수백 개 조각 중 **그 페이지에 실제로 쓰인
  글자의 조각만** 받는다. 한국어 사이트의 표준 해법이다.
- **버린 대안 1: 셀프호스팅 풀 woff2** — 외부 의존은 없지만 1.2MB를 매번 받는다.
- **버린 대안 2: 직접 서브셋 빌드** — 가장 작지만 빌드 파이프라인이 하나 늘고, 나중에 문구를
  바꾸면 글리프가 빠져 두부(□)가 난다. 이 프로젝트 규모에 맞지 않는다.
- **오프라인이면?** 폰트만 폴백 스택으로 떨어지고 화면은 정상 동작한다. `docker compose`
  시연이 네트워크 없이 돌아도 레이아웃은 안 깨진다.

`font-display: swap`은 위 CSS에 이미 들어 있다 — 폰트를 기다리며 글자가 안 보이는 구간(FOIT)이
생기지 않는다.

**Inter도 같이 로드한다.** 라틴 자리(`BEAUTY BOY`, `SALE`, 숫자, 가격)가 전부 Inter를
기대하고 있고, 지금은 그것도 시스템 폰트로 그려진다. Inter는 Google Fonts의 가변 축을 쓴다:

```html
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link rel="stylesheet"
      href="https://fonts.googleapis.com/css2?family=Inter:wght@400..800&display=swap" />
```

가중치를 `400..800` 가변 범위로 받는 이유: `index.css`의 `--fw-*` 토큰이 400·600을 쓰고
CSS 곳곳에 600·700·800이 있다. 개별 굵기를 열거하면 나중에 토큰이 하나 늘 때 그 굵기만
합성(faux bold)으로 그려지고 아무도 눈치채지 못한다. 가변 축은 그 클래스를 없앤다.

`--font-body` 선언 자체는 **바꾸지 않는다.** 스택은 이미 옳고, 없던 실물을 채우는 것이 이
태스크다.

### 결정 6 — 햄버거는 `DESIGN.md`가 이미 정한 것을 구현하는 일이다

새로 설계하지 않는다. 문서에 이미 있다.

- `DESIGN.md` Breakpoints: `xs | 768px | Top nav collapses to a hamburger`
- `DESIGN.md` Collapsing Strategy → Nav: *"Centred desktop menu collapses into a single
  hamburger that opens an overlay sheet; the right-side `{button-primary}` stays visible above
  the hamburger as the persistent action."*

현재 `Header.css:159`는 접기만 하고 펼칠 수단을 안 만들었다.

```css
@media (max-width: 768px) {
  /* 좁은 화면에서는 검색바를 지키고 주요 메뉴를 접는다 */
  .bb-header__primary-nav { display: none; }
}
```

주석은 "접는다"인데 코드는 **없앤다**이다. 768px 이하에서 `PRIMARY_NAV`의 세 링크(루틴 가이드 ·
랭킹 · 전체 상품)로 가는 길이 사라진다. 랜딩 헤더(`Header.css:85`)도 `LANDING_NAV` 네 개가
같은 방식으로 사라진다.

**뷰티보이에서의 "persistent action"은 장바구니와 계정이다.** 원본의 "Try Runwai" 자리에
해당하는 것 — 이 둘은 햄버거 안으로 넣지 않고 상단바에 남긴다. 돈으로 가는 길과 로그인 상태
표시는 항상 보여야 한다.

동작 사양:

| 항목 | 사양 |
|---|---|
| 버튼 위치 | 상단바 우측 끝, 장바구니·계정 **오른쪽** |
| 버튼 표시 조건 | 768px 이하에서만 (`.bb-header__primary-nav`가 숨는 그 폭) |
| 버튼 크기 | 44×44 이상 |
| 접근성 | `aria-label="메뉴 열기"`/`"메뉴 닫기"`, `aria-expanded`, `aria-controls` |
| 열림 형태 | 상단바 아래로 펼치는 시트. 링크는 세로 1열, 각 항목 최소 44px 높이 |
| 닫히는 조건 | ① 링크 클릭 ② 버튼 재클릭 ③ **Esc** ④ 라우트 변경 |
| 라우트 변경 시 | `useLocation().pathname`이 바뀌면 닫는다 — 안 닫으면 이동 후에도 시트가 남는다 |
| 769px 이상으로 넓어지면 | 열린 상태가 남아 있어도 시트는 안 보인다(미디어쿼리로 숨김). 상태도 닫아 준다 |
| 시각 언어 | 흰 캔버스 + 검정 잉크. **`signal-*`을 배경으로 칠하지 않는다** |

**바깥 클릭으로 닫지 않는다.** 시트가 상단바 바로 아래 붙는 형태라 오버레이가 없고, 바깥
클릭 감지를 붙이면 그 아래 콘텐츠의 첫 클릭을 삼킨다. Esc·재클릭·링크 클릭 셋으로 충분하다.

### 결정 7 — 터치 타깃은 `DESIGN.md`가 이미 44px을 요구한다

`DESIGN.md` "Touch Targets" 절이 `44×44 WCAG target`을 기준으로 쓰여 있고 모바일 버튼 48px을
명시한다. 구현이 안 따라갔을 뿐이다.

**측정은 `<label>`을 고려해서 한다.** `input` 요소만 재면 틀린다 — 라디오·체크박스가
`<label>`로 감싸여 있으면 **실제 탭 영역은 라벨 전체**다. 이 프로젝트의 라디오 7곳은 전부
그 형태이므로(`SkinProfileFields.tsx:120`의 `<label class="bb-skin-type-card">`가 대표)
**폼 입력은 이미 44px을 넘는다.** 손대지 않는다.

`el.closest('label') || el`로 다시 잰 390px 실측:

| 요소 | 실측 | 어디 | 왜 고치나 |
|---|---|---|---|
| 헤더 링크 (장바구니·닉네임·로그아웃) | **18px** 높이 | `Header.css` | 계정·장바구니 진입로 |
| 수량 스테퍼 `−`/`+` | **32×32** | `QuantityStepper.css` | 장바구니 수량 = 결제 금액 |
| 찜 하트 ♡ | **32×32** | `GoodsCard.css` | 목록의 유일한 즉시 행동 |
| 메인 카테고리 내비 | **29px** 높이 | `Main.css` | 탐색 주 경로의 시작점 |

**범위를 좁게 자른다** — 화면당 최대 36개가 44px 미만이지만 전부 고치면 태스크가 부풀고 시각
회귀 표면이 넓어진다. 이번에 손대는 것은 위 넷뿐이고, 넷 다 **"손님이 반드시 눌러야 하는"**
것이다. 경계선에 있는 것들(`bb-chip` 57×35, `bb-list-toolbar__pill` 93×38, `bb-tag` 41×27)은
남긴다 — 35~38px은 오탭이 잘 나지 않는 구간이고, 손대면 목록 툴바 레이아웃이 통째로 밀린다.

키우는 방식은 **타이포를 바꾸지 않고 패딩·최소높이로만** 한다. `DESIGN.md`가
*"`{nav-link}` items get `{spacing.sm}` vertical padding … expanding the tap target without
changing typography"* 라고 방법까지 지정해 뒀다. 폰트 크기를 올리면 헤더 균형이 깨진다.

수량 스테퍼와 찜 하트는 **원의 시각적 크기는 32px 그대로 두고 히트영역만** 44px로 넓힌다
(`::before` 확장 또는 투명 패딩). 원을 키우면 카드와 장바구니 줄의 밀도가 바뀐다.

3. **두 브랜치를 머지한 뒤** `npm run test:e2e`를 한 번 돌린다. 백엔드는 반드시 **`e2e`
   프로필**로 띄운다 — [[e2e-needs-e2e-profile-backend]] (compose 백엔드로 돌리면 토스 401로
   거짓 적신호가 뜨고, 시드 계정 장바구니도 비워야 한다).
4. **compose 이미지를 다시 빌드한다.** 현재 떠 있는 프론트 컨테이너는
   `2026-07-28T14:23Z` 빌드로, 주문 페이징 머지(`d18a4dd`, `15:01Z`)보다 낡았다. 그래서
   `localhost:3000/mypage/orders`가 지금 `n.map is not a function`으로 크래시한다(소스는

   ```
   docker compose up -d --build frontend backend
   ```
   이건 이번 계획의 산출물과 무관한 **기존 상태**지만, 머지 후 시연하면 같은 화면을 보게 되므로
   여기서 같이 닫는다.
5. 머지 후 `docs/plans/2026-07-26-다음-작업.md` §5-1의 7건에 종결 표시(`✅ 완료` + 커밋 해시)를

## 6. 범위 밖 — 브레이크포인트 9종 수렴은 **하지 않는다**

§5-1이 "브레이크포인트도 900/768/767/820/640/600/480px로 7종이 혼재해 시스템이라기보다
임기응변"이라고 적은 항목이다. 실측은 **9종 35회**다.

| 폭 | 횟수 | 대표 사용처 |
|---|---|---|
| 900px | 14 | Cart, Order, Sets, Routine, GoodsList, MyPage 4종, Admin |
| 768px | 8 | Header 3, GoodsGrid, Detail, Home, RoutineSection, AdminGoods |
| 640px | 5 | Header, RoutineStepCard, SetBand, Button, Showcase |
| 767px | 3 | CautionPanel, ListToolbar, SetBand — **Task 2-6이 768로 고친다** |
| 480 / 600 / 820 / 1024 / 1440 | 각 1 | SkinProfileStep, CartLine, AuthLayout, GoodsGrid ×2 |

**안 하기로 한 근거:**

1. **손님에게 보이는 손해가 없다.** 증상이 드러나는 조건이 "창을 850px 근처로 맞춤"(900px과
   768px 축이 갈리는 구간) 또는 "화면 폭이 정확히 768px"이다. 실기기 중 걸리는 것이 거의 없다.
   390px 폭 실측에서 **12개 화면 전부 가로 오버플로 0**이었다 — 모바일 실사용에서 깨지는
   지점이 아니다.
2. **비용이 §5-1에서 가장 크다.** 숫자를 옮기면 접히는 시점이 바뀌므로 CSS 21개 파일 35개
   규칙에 대해 **화면 전수 스크린샷 대조**가 필요하다. CLAUDE.md의 스크린샷 DoD를 지키면
   이 계획의 나머지 전부를 합친 것보다 크다.
3. **부채가 자라지 않는다.** 1차 MVP가 완성된 상태라 새 화면이 대량으로 추가될 계획이 없다.
   "지금 안 하면 나중에 더 비싸진다"가 성립하지 않는다.

`DESIGN.md`의 Breakpoints 절 아래에 이 결정을 기록한다(Task 2-6 Step 6). 문서와 코드가
갈라진 채로 두지 않기 위해서다 — **인지하고 우선순위를 매긴 부채**와 **방치된 부채**는 다르다.

단 `767px` 3곳은 예외로 이번에 고친다. 수렴이 아니라 **오타 수정**이고, 나머지 8곳이 768px인데
셋만 767px이라 768px 화면에서 그 셋만 데스크톱 배치로 남는다. 시각 회귀 위험이 없다.

### 이번에도 §5-1에 남기는 것 (다음 웨이브 후보)

- 브레이크포인트 9종 수렴 (위 근거로 보류)
- queryKey 팩토리의 나머지 키(`goods`, `ranking`, `search` …) — 하드코딩이 한 곳뿐이라
  팩토리가 얻는 게 없다. 두 곳 이상이 되는 날 옮긴다.
- 터치 타깃 44px의 나머지 — 이번엔 헤더 링크·수량 스테퍼·찜 하트·메인 카테고리 내비 넷만 했다.
  경계선에 있는 것들(`bb-chip` 57×35, `bb-list-toolbar__pill` 93×38, `bb-tag` 41×27)은
  35~38px이라 오탭이 잘 나지 않고, 손대면 목록 툴바 레이아웃이 통째로 밀린다.
  **폼 입력(라디오·체크박스)은 이월이 아니라 애초에 문제가 아니다** — 전부 `<label>`이 감싸고
  있어 실제 탭 영역이 이미 44px을 넘는다. `input` 요소만 재면 13×13으로 보이므로 다시 "결함"으로
  올라오지 않게 여기 적어 둔다.
