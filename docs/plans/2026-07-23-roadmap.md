# 뷰티보이 구현 로드맵 (1차 MVP)

> 설계 근거: `docs/superpowers/specs/2026-07-23-beautyboy-design.md`
> 실행 모델: `CLAUDE.md` (오케스트레이터 + 서브에이전트, 터미널 1개 = worktree 1개 = 브랜치 1개)
> 상세 태스크는 웨이브별 계획서(`docs/plans/2026-07-23-waveN-*.md`)에 있다. 이 문서는 웨이브 구조·의존성·공유 계약의 유일한 진실이다.

## 웨이브 구조

```
Wave 0 (직렬, 터미널 1개) ─ Foundation
  스캐폴딩(backend/frontend), 공통 계약, Flyway 코어, member/auth(JWT), 프론트 셸+인증 화면
        │
Wave 1 (병렬, 터미널 2개)
  T1: catalog + ingredient + 시드 데이터        [브랜치 feat/catalog]
  T2: 프론트 디자인시스템 + 공통 컴포넌트(상품카드/레이아웃, MSW mock 기반)  [feat/front-base]
        │
Wave 2 (병렬, 터미널 3개)
  T1: search + ranking                          [feat/search-ranking]
  T2: cart + order + payment(토스, ★opus)       [feat/order-payment]
  T3: review + qna + wishlist                   [feat/review]
        │
Wave 3 (병렬, 터미널 2개)
  T1: delivery(오늘드림 재고차감 ★opus) + routine + compat(궁합엔진 ★opus)  [feat/delivery-routine]
  T2: 프론트 페이지 조립: 메인/목록/상세/검색/랭킹 (실API 연동)             [feat/front-pages]
        │
Wave 4 (직렬, 터미널 1개) ─ 통합
  주문·결제·루틴 프론트 통합, 마이페이지, admin 최소 CRUD,
  통합·E2E(Playwright), 시드 확충(상품 150개), README
```

- ★opus = CLAUDE.md 모델 배분 예외 태스크. 그 외 서브에이전트는 sonnet.
- 각 웨이브 착수 시점에 해당 웨이브 상세 계획서를 먼저 작성·커밋한 뒤 worktree를 딴다.
- 웨이브 종료 = 모든 터미널 브랜치가 리뷰(테스트 통과 + 파일 소유권 준수) 후 main에 머지된 상태.

### Wave 2 병렬 분기 전 사전 정리 (2026-07-24 완료)

터미널 3개가 같은 파일을 동시에 만지는 지점을 분기 **전에** 미리 닫았다. 아래 파일들은
Wave 2 각 터미널이 **열지 않는다** — 필요가 생기면 수정하지 말고 보고한다.

- **`common/ErrorCode.java`** — 공유 계약이라 "자기 접두사 상수 추가"만 허용돼 있지만, 세 터미널이
  같은 enum 끝에 append하면 git이 3방향 충돌로 본다. `SEARCH_*` `RANKING_*` `CART_*` `ORDER_*`
  `PAYMENT_*` `REVIEW_*` `QNA_*` `WISHLIST_*`를 **선점해 한 커밋으로 넣어뒀다.**
- **`build.gradle.kts`** — 동결. Testcontainers 도입이 이 파일을 만지므로 분기 전에 끝냈다.
  T2(결제)의 토스 호출은 `RestClient`(starter-web 포함)로 충분해 **추가 의존성이 없다.**
  T1(랭킹) 조회수의 Redis INCR은 **1차 범위에서 제외** — DB 카운터로 가고 Redis는 Wave 4로 미룬다
  (병렬 중 이 파일을 열지 않기 위함).
- **`config/SecurityConfig.java`** — Wave 0에서 공개 목록을 선반영해뒀다. `/search/**` `/rankings`는
  이미 열려 있고 T2의 인증 경로는 `anyRequest().authenticated()`로 자동으로 떨어진다. 손대지 않는다.
- **랭킹의 교차 도메인 의존** — 점수 `판매×3 + 찜×2 + 조회×1`에서 판매는 `order`(T2), 찜은
  `wishlist`(T3) 소유다. ranking이 그 테이블을 직접 읽으면 "패키지 = 서비스 경계" 위반이므로
  **필요한 쪽이 정의하고 가진 쪽이 구현하는** 인터페이스로 갈랐다(의존성 역전):
  `ranking.SalesStatProvider` · `ranking.WishStatProvider`. **이 시그니처는 확정 계약이다.**
  실 구현이 없는 동안은 `RankingStatFallbackAutoConfiguration`의 빈 맵 구현으로 앱이 뜬다
  (`@ConditionalOnMissingBean`이 제대로 동작하도록 일반 `@Configuration`이 아니라 자동 설정으로 뒀다 —
  사용자 설정끼리는 처리 순서가 보장되지 않는다). **T2·T3 머지 후 폴백이 아니라 실 구현이 주입되는지
  반드시 확인한다** — 조용히 폴백이 남으면 랭킹이 영원히 조회수 랭킹이 된다.

### Wave 3 T2 메인 페이지 구성 — 확정 (2026-07-23)

> **상세 사양·태스크·실행 프롬프트는 `docs/plans/2026-07-23-landing-main-composition.md`.**
> 아래는 요약이며, 착수할 때는 그 문서를 읽는다.

레퍼런스: <https://pangrampangram.com/> (세로로 쌓인 풀블리드 사진 섹션 + 거대 디스플레이 타이포).
**메인은 스크롤 순서가 곧 스킨케어 루틴 순서다.** 타겟이 "뭘 사야 할지 모르는 남성"이므로
순서 자체가 교육이 되고, 이것이 올리브영 클론과의 차별점이다.

**루틴 단계 ↔ 카테고리 매핑** (카탈로그 API의 접두사 필터를 그대로 쓴다 — `GET /goods?categoryCode=`)

| 단계 | 이름 | categoryCode | 담기는 것 |
|---|---|---|---|
| 1 | 클렌징 | `C002` | 클렌징폼 · 클렌징오일/밤 · 필링/스크럽 |
| 2 | 토너/스킨 | `C001001` | 수분토너 · 진정토너 |
| 3 | 에센스/세럼 | `C001002` | 고보습에센스 · 미백세럼 |
| 4 | 로션/크림 | `C001003` | 데일리로션 · 고영양크림 |
| 5 | 선크림 | `C004001` | 선크림 |

- **단계 깊이가 섞이는 것은 의도적이다** — 단계는 깊이가 아니라 의미로 정한다. 클렌징은 대분류
  하나가 곧 한 단계고, 스킨케어는 대분류 하나 안에 3단계가 들어 있다.
- **루틴 순서는 카테고리 트리로 표현하지 않는다.** 카테고리는 "무엇인가"(분류), 루틴은 "언제
  바르는가"(순서)로 축이 다르다. 하나로 억지로 합치면 둘 다 망가진다. 메인은 위 매핑을 **명시적
  상수**로 들고 굴린다. CLAUDE.md "돈과 재고는 서버, 취향은 클라이언트"에 해당하므로 프론트 상수로
  시작하고, 필요해지면 Wave 3의 `routine` 도메인으로 옮긴다.
- **아침/저녁을 구분하지 않는다.** 기본 루틴 하나만 둔다(선크림이 마지막인 것은 그 결과다).
- **루틴 축에 없는 카테고리는 메인의 루틴 섹션에 넣지 않는다** — 헤어·바디(`C003`),
  쉐이빙·그루밍(`C005`), 메이크업(`C006`), 선스틱·애프터선(`C004002`·`C004003`)은 별도 진입점으로.
- **긴 스크롤 대비**: 5섹션 × 풀블리드면 모바일에서 상품 도달까지 스와이프가 길다. 루틴 단계
  앵커 네비 또는 sticky 진행 표시를 함께 설계한다(`DESIGN.md` UX 계약의 sticky 헤더 오프셋 규칙 연장).
- **사진은 무료 스톡**(Unsplash 등)을 쓴다. 실제 브랜드 제품 사진은 설계 11장에 따라 금지.
- **로그인/가입은 이 서사에 넣지 않는다.** 메인은 탐색·설득, 인증은 과업 완수로 목적이 다르다.
  단 `Layout`(헤더)은 계속 공유한다 — 헤더를 빼면 인증 화면에서 빠져나갈 길이 사라진다.
  시각적 임팩트가 필요하면 split(좌: 스톡 사진 + 큰 타이포 / 우: 폼) 패턴을 쓴다.

## 병렬 안전을 위한 공유 계약

**1. Flyway 버전 대역** (충돌 방지 — 자기 대역 밖 번호 사용 금지)

| 대역 | 소유 | 내용 |
|---|---|---|
| V1~V9 | Wave 0 | member, address, 공통 |
| V10~V19 | Wave 1 T1 | category, brand, goods, goods_option, promotion, ingredient 계열 |
| V20~V29 | Wave 2 T1 | **사용: V20 search_keyword_log · V21 goods_daily_stat+ranking_snapshot · V22 goods ngram FULLTEXT** (머지 완료) |
| V30~V39 | Wave 2 T2 | **사용: V30 cart_item · V31 orders+order_item · V32 payment** (머지 완료). point_history는 소비처 없어 미생성 |
| V40~V49 | Wave 2 T3 | review 계열, qna, wishlist |
| V50~V59 | Wave 3 T1 | store, store_stock, routine 계열 |
| V60~ | Wave 4 | 보정 |

**2. 공통 코드 소유권**: `common` 패키지(ApiResponse, ErrorCode, BusinessException, 전역 핸들러), 루트 빌드 설정, `docker-compose.yml`은 **Wave 0 산출물 이후 동결**. 수정 필요 시 보고만.

**3. 도메인 간 인터페이스**: 타 도메인 접근은 `*QueryService` / `*CommandService` 인터페이스 경유 (CLAUDE.md 규칙). 예: `review`의 구매 인증은 `order.OrderQueryService.hasDeliveredItem(memberId, goodsNo)`를 호출 — Wave 2 T3는 이 인터페이스에 맞춰 개발하고, 실 구현은 T2가 제공(머지 시 결합).

**4. ErrorCode 네임스페이스**: 승인된 접두사 목록과 규칙은 **설계 문서 9장이 진실**이다. 여기서는 운용 규칙만 — 자기 도메인 접두사로 **상수 추가만** 허용하고 기존 상수는 수정하지 않는다.

**5. 테스트 규약**: 단위/슬라이스 = H2(MySQL 모드, Flyway off, ddl-auto=create-drop) — 터미널 병렬 안전. 공유 MySQL·토스 API를 만지는 통합/E2E는 Wave 4 직렬 웨이브에서만.

**6. API 응답 계약**: `ApiResponse` 봉투, `PageResponse<T>` 페이징 포맷, `GoodsListItem` 카드 아이템,
공개 엔드포인트 목록 — 전부 **설계 문서 7장이 진실**이다. 이 문서는 형태를 다시 적지 않는다
(같은 사실이 두 곳에 있으면 언젠가 한쪽만 바뀐다).

여기서 정하는 것은 **운용 규칙**뿐이다:

- `common`의 `ApiResponse`·`PageResponse`·`ErrorResponse`·전역 핸들러는 Wave 0 산출물 이후 **동결**.
  도메인별 페이징 타입을 새로 만들지 않는다.
- `SecurityConfig`는 Wave 0에서 설계 7장 공개 목록을 **선반영 완료**했다. **이후 웨이브는 이 파일을
  수정하지 않는다** — Wave 2는 터미널 3개가 병렬로 도는데 각자 여기를 고치면 하필 인가 설정에서
  3방향 충돌이 난다. 공개가 필요한 경로가 생기면 설계 7장을 먼저 고치고 보고한다.
- `GoodsListItem`은 **미래 웨이브가 채울 필드까지 포함한 상태로 동결**됐다. Wave 1 T1은 못 채우는
  값을 기본값(`0.0`/`0`/`false`)으로 내고, T2는 그 형태로 카드와 mock을 만든다. 그래야 Wave 2·3에서
  값이 채워질 때 프론트를 고치지 않는다.
- 상품 **상세**(`/goods/{goodsNo}`) 응답 형태는 Wave 1 T1 계획서가 정의한다 — 상세 페이지 조립이
  Wave 3 T2 몫이라 지금 전역 계약으로 고정할 이유가 없다.

**7. 프론트 디자인 계약**: 시각 언어(색·타이포·간격·컴포넌트 사양)는 루트 `DESIGN.md`가 진실이다.
프론트 태스크는 이 문서의 토큰 이름을 직접 참조하고 hex를 손으로 옮겨 적지 않는다.

## 웨이브별 완료 기준 (Definition of Done)

- **W0**: `./gradlew test` 녹색 + 가입→로그인→내정보 조회가 curl로 재현 + 프론트에서 로그인 성공
- **W1**: 카테고리 트리·상품 목록/상세·성분 API가 시드 데이터로 응답 + 프론트 상품카드가 MSW mock으로 렌더
- **W2**: 검색/랭킹/장바구니 API + 토스 테스트 결제 승인-검증 통과(결제 2단계) + 리뷰 CRUD(구매인증 포함, 인터페이스 스텁)
- **W3**: 오늘드림 판정·조건부 차감(동시성 테스트 포함) + 루틴 조회·궁합 진단 + 프론트 탐색 플로우가 실API로 동작
- **W4**: 탐색→루틴 담기→주문→결제 E2E 녹색, admin에서 상품/루틴 CRUD 가능, README에 실행법
