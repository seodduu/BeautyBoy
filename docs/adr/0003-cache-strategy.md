# ADR 0003 — 읽기 캐시 전략: 대상 선정, TTL과 무효화, 워밍, 폴백

- **날짜**: 2026-07-29
- **상태**: 채택됨 (구현·측정 완료)
- **관련**: [부하 리포트](../loadtest/2026-07-29-report.md) §3.6,
  [설계 문서](../plans/2026-07-29-traffic-hardening-design.md) §6

## 맥락

쓰기(주문 확정)를 이벤트로 뺐다면, 읽기는 캐시로 버텨야 한다. 문제는 **무엇을 캐시할지**다.
전부 캐시하면 무효화 지점이 폭발하고, 무효화를 한 군데라도 빠뜨리면 **틀린 데이터를 빠르게
서빙**하게 된다. 캐시의 진짜 비용은 메모리가 아니라 정합성이다.

Redis는 이 프로젝트에 이미 있었지만 "선택" 취급이었다(조회수 버퍼, 없으면 DB 폴백).
캐시가 핵심 경로에 들어오면서 **필수로 승격**됐고, 그럼에도 **Redis가 죽으면 서비스는
살아야 한다**는 기존 폴백 철학은 그대로 지켜야 했다.

## 결정

Cache-Aside. Spring `@Cacheable` + `RedisCacheManager` 기반, 캐시명 셋으로 한정한다.
키에는 `v1:` 버전 프리픽스를 붙인다(`CacheConfig.prefixCacheNameWith("v1:")`) —
값 스키마가 바뀌면 프리픽스를 올려 통째로 무효화한다.

### 1. 대상 선정 기준

**"트래픽이 몰리는가 × 원본 비용이 있는가 × 무효화 지점이 명확한가"** 셋을 모두 만족하는
것만 캐시한다.

| 캐시명 | 대상 | 트래픽 | 원본 비용 | 무효화 지점 |
|---|---|---|---|---|
| `ranking` | 랭킹 조회 | **최고** (browse의 70%) | 낮음(이미 스냅샷 테이블) | 배치의 스냅샷 교체 직후 — 명확 |
| `goodsList` | 상품 목록 + 검색 | 높음 | 중간(조건부 쿼리 + count + 별점/찜 조인) | 상품 등록/수정 — 명확 |
| `compat` | 성분 궁합 판정 | 중간 | **높음**(성분 집합 × 규칙표 계산) | 성분 변경 — 명확 |

**캐시하지 않은 것과 그 이유**: 장바구니·주문·마이페이지는 개인별 쓰기가 잦아 히트율이
낮고 무효화 지점이 흩어진다. 상품 상세는 조회수 증가라는 쓰기가 매 조회에 붙어 있어
캐시-쓰기 상호작용이 복잡해진다. **랭킹은 원본 비용이 낮은데도 넣었는데**, 최고 트래픽
경로여서 절대 호출 수의 절감폭이 크고 스탬피드 실험의 소재가 되기 때문이다.

### 2. 키 설계 — 개인화가 함정이었다

설계 §6은 키를 `랭킹:{기간}:{카테고리}` 식으로 잡았다. **구현에서 바꿨다.**
세 응답 중 둘이 **개인화**돼 있었기 때문이다.

- `RankingItem.wished()`, `GoodsListItem.wished()`, `SearchResultItem.wished()`는
  **조회자의 찜 여부**다. 카테고리만 키로 쓰면 먼저 조회한 사용자의 찜 상태가 다른 사용자에게
  그대로 캐시돼 나간다 — 빠른 오답이다.
- 그래서 키에 `viewerId`/`memberId`를 붙였다: 랭킹은 `카테고리:viewerId`,
  목록은 `카테고리:정렬:페이지:필터해시:viewerId`, 검색은 `search:` 접두 + 같은 형태.
- **궁합만 개인화가 없다** — 반환값이 성분 집합과 규칙표로만 결정되고 조회자를 참조하지 않는다.
  그래서 키가 `min(a,b):max(a,b)`로 순수하다(`CacheKeys.compat` — (a,b)와 (b,a)가 같은 키여야
  한다. `worstVerdicts`가 무순서 쌍만 검사하므로 판정값도 실제로 대칭이다).

필터 조합은 **이름 오름차순으로 `k=v&` 연접한 문자열의 SHA-256 앞 16 hex**로 눌러 키 폭발을
막는다(`CacheKeys.goodsList`). 순서를 고정하지 않으면 같은 조합이 다른 키가 되어
**히트율이 조용히 죽는다** — 에러가 나지 않아 발견도 어렵다.

개인화를 키에 넣은 대가는 **히트율 하락**이다. 회원 수만큼 키가 늘어난다. 그래도 오답보다는
낫고, 익명 트래픽(viewerId=null)이 조회의 다수라 캐시 효과 자체는 남는다.

### 3. TTL

`CacheConfig`의 값이 진실이다.

| 캐시 | TTL | 근거 |
|---|---|---|
| `ranking` | **10분** | 배치가 주기 실행이라 그보다 오래 들고 있을 이유가 없다 |
| `goodsList` | **5분** | 가격·품절 변경이 5분 넘게 안 보이면 사용자가 알아챈다 |
| `compat` | **24시간** | 성분 데이터는 거의 변하지 않는다. 원본 비용이 가장 높아 오래 들고 있는 이득이 크다 |

검색은 새 캐시명을 만들지 않고 `goodsList` 캐시에 `search:` 접두로 얹었다 — **TTL이 등록된
캐시명이 셋뿐이라 새 이름을 쓰면 TTL 없이 무한 보관되기 때문**이다. 이런 종류의 사고는
조용히 일어난다.

### 4. 무효화 — 목록은 전체 clear로 단순화했다 (설계에서 벗어난 결정)

설계 §6은 "상품 등록/수정 시 **카테고리 패턴 삭제**"라고 적었다. 구현은
**`allEntries = true` 전체 clear**로 바꿨다(`AdminGoodsService.create` / `update`).

근거:

- 패턴 삭제는 Redis `SCAN` + 키 구조에 대한 결합을 만든다. 키 포맷을 바꿀 때마다 무효화 코드가
  따라 깨지고, 깨져도 **에러 없이 낡은 데이터가 남는다.**
- 상품 등록/수정은 **admin 액션이라 빈도가 극히 낮다.** 전체 clear의 비용(다음 조회 몇 건이
  미스)이 패턴 삭제의 복잡도보다 싸다.
- 정합성 방향이 안전한 쪽이다 — 과대무효화는 느려질 뿐이지만, 과소무효화는 틀린다.

같은 이유로 `update`는 `compat` 캐시도 함께 비운다. 현재 `AdminGoodsSaveRequest`에 성분 필드가
없어 실제 "성분 변경" 쓰기 경로가 아직 없지만, 그 경로가 생기기 전까지는 **선제적 과대무효화**로
둔다.

랭킹은 TTL 10분에 더해 **배치가 스냅샷을 교체한 직후 캐시를 비운다**(다음 항목).

### 5. 스탬피드 대응 — 워밍(1안)을 채택하고 soft-TTL(2안)을 채택하지 않았다

랭킹 배치가 스냅샷을 교체한 뒤 캐시를 **clear만 하면**, 그 직후 몰리는 조회가 한꺼번에
미스로 DB를 때린다(cache stampede). 대응 후보는 둘이었다.

- **1안 — 배치 직후 워밍**: 캐시를 비우고 **즉시 다시 채운다.**
- **2안 — 확률적 soft-TTL**: 만료 임박 시 일부 요청만 재계산하게 해 동시 재계산을 흩는다.

**1안을 채택했다.** 근거는 "이미 있는 것을 쓴다"이다 — 랭킹 배치가 이미 주기적으로 돌고,
캐시가 무효화되는 **정확한 시점을 우리가 알고 있다.** 그 시점에 미리 구우면 스탬피드가 애초에
생기지 않는다. soft-TTL은 **만료 시점을 모를 때** 쓰는 확률적 완화책이라, 시점을 아는 상황에서
쓰면 더 복잡하면서 더 약하다. 2안은 워밍이 불충분한 것으로 드러날 때의 예비안으로 남긴다.

구현(`RankingCacheRefresher.refreshAfterRebuild`)의 두 가지 판단:

- **워밍은 `viewerId = null`(비로그인) 슬롯만 채운다.** 로그인 사용자의 캐시 키는 회원마다
  달라 미리 구울 수 없다(§2). 익명 트래픽이 조회의 대다수라 스탬피드 대응 목적은 달성된다.
- **`CacheManager`를 `ObjectProvider`로 받는다.** 캐시 토글이 꺼져 있으면 `CacheManager` 빈
  자체가 없는데, 그 상태에서도 배치는 정상적으로 돌아야 한다. 캐시 매니저·캐시 부재 모두
  조용히 스킵한다(NPE 금지).

목록·궁합에는 스탬피드 대응을 넣지 않았다. 만료가 한 시점에 몰리지 않고(요청마다 TTL이 개별로
시작한다), 원본 비용이 랭킹 배치 직후만큼 집중되지 않는다.

### 6. Redis 장애 시 DB 직행 폴백

**기본 `SimpleCacheErrorHandler`는 예외를 rethrow한다 — 즉 캐시 장애가 곧 서비스 장애가 된다.**
반드시 오버라이드해야 한다.

`CacheConfig.errorHandler()`가 get/put/evict/clear 네 경우의 예외를 전부 삼키고 `warn` 로그만
남긴다. 그러면 `@Cacheable` 메서드는 원본 구현으로 직행한다. **Redis가 통째로 죽어도
랭킹·목록·궁합 조회는 느려질 뿐 살아 있다.** 조회수 버퍼가 Redis 실패 시 DB 카운터로
폴백하는 것과 같은 철학이다.

캐시 인프라 전체가 `beautyboy.cache.redis` 토글 아래 있다(기본 false) — Redis 없이도 앱이 뜬다.

## 결과

**측정된 것** (부하 리포트 §3.6, `browse` 시나리오)

| 지표 | 캐시 없음 | 캐시 적용 |
|---|---|---|
| p95 | 74.324 ms | **8.023 ms** (9.3배) |
| p99 | 79.317 ms | 9.951 ms |
| RPS | 2,483.61481 | **15,910.27012** (6.4배) |
| 히트율 | — | 1,931,836 hit / 3 miss (99.99984%) |

**이 히트율은 과장하면 안 되는 숫자다.** 부하 스크립트가 `CATEGORY_CODE`/`GOODS_A`/`GOODS_B`를
고정해 조회하므로 **캐시 키 공간이 사실상 3개**다(미스 3건은 최초 요청 3개). 실제 트래픽은
카테고리·정렬·페이지·필터 조합에 **회원별 개인화 키(§2)**까지 곱해지므로 히트율이 이보다
**상당히 낮다.** 검색은 검색어가 롱테일이라 특히 낮다. 즉 이 측정은 **"캐시가 맞을 때의
상한"**을 잰 것이지 운영 히트율을 잰 것이 아니다.

**치른 것**

- 개인화를 키에 넣어 히트율을 스스로 낮췄다(오답을 피하기 위한 의도적 선택).
- admin의 상품 등록/수정 한 번이 `goodsList` 캐시 전체를 날린다(과대무효화, 의도적).
- 캐시명이 셋으로 고정돼, 새 캐시를 추가할 때 `CacheConfig`의 TTL 맵 등록을 잊으면 무한
  보관된다 — 검색이 `search:` 접두로 기존 캐시명에 얹힌 이유가 이것이다.
- `@EnableCaching(proxyTargetClass = true)`가 필요했다. `GoodsService`처럼 인터페이스를 구현하면서
  구체 타입으로도 주입되는 클래스에 `@Cacheable`을 걸면 JDK 동적 프록시가 인터페이스만 구현한
  프록시를 만들어 컨텍스트가 죽는다. CGLIB 프록시로 강제해 해결했다.
