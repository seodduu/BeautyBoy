# 뷰티보이 구현 로드맵 (1차 MVP)

> 설계 근거: `docs/superpowers/specs/2026-07-23-beautyboy-design.md`
> 실행 모델: `CLAUDE.md` (오케스트레이터 + 서브에이전트, 터미널 1개 = worktree 1개 = 브랜치 1개)
> 상세 태스크는 웨이브별 계획서(`docs/plans/2026-07-23-waveN-*.md`)에 있다. 이 문서는 웨이브 구조·의존성·공유 계약의 유일한 진실이다.

## 웨이브 구조

```
Wave 0 (직렬, 터미널 1개) ─ Foundation
  스캐폴딩(backend/frontend), 공통 계약, Flyway 코어, member/auth(JWT), 프론트 셸+인증 화면
        │
Wave 1 (병렬, 터미널 2개)
  T1: catalog + ingredient + 시드 데이터        [브랜치 feat/catalog]
  T2: 프론트 디자인시스템 + 공통 컴포넌트(상품카드/레이아웃, MSW mock 기반)  [feat/front-base]
        │
Wave 2 (병렬, 터미널 3개)
  T1: search + ranking                          [feat/search-ranking]
  T2: cart + order + payment(토스, ★opus)       [feat/order-payment]
  T3: review + qna + wishlist                   [feat/review]
        │
Wave 3 (병렬, 터미널 2개)
  T1: delivery(오늘드림 재고차감 ★opus) + routine + compat(궁합엔진 ★opus)  [feat/delivery-routine]
  T2: 프론트 페이지 조립: 메인/목록/상세/검색/랭킹 (실API 연동)             [feat/front-pages]
        │
Wave 4 (직렬, 터미널 1개) ─ 통합
  주문·결제·루틴 프론트 통합, 마이페이지, admin 최소 CRUD,
  통합·E2E(Playwright), 시드 확충(상품 150개), README
```

- ★opus = CLAUDE.md 모델 배분 예외 태스크. 그 외 서브에이전트는 sonnet.
- 각 웨이브 착수 시점에 해당 웨이브 상세 계획서를 먼저 작성·커밋한 뒤 worktree를 딴다.
- 웨이브 종료 = 모든 터미널 브랜치가 리뷰(테스트 통과 + 파일 소유권 준수) 후 main에 머지된 상태.

## 병렬 안전을 위한 공유 계약

**1. Flyway 버전 대역** (충돌 방지 — 자기 대역 밖 번호 사용 금지)

| 대역 | 소유 | 내용 |
|---|---|---|
| V1~V9 | Wave 0 | member, address, 공통 |
| V10~V19 | Wave 1 T1 | category, brand, goods, goods_option, promotion, ingredient 계열 |
| V20~V29 | Wave 2 T1 | search_keyword_log, goods_daily_stat, ranking_snapshot |
| V30~V39 | Wave 2 T2 | cart_item, orders, order_item, payment, point_history |
| V40~V49 | Wave 2 T3 | review 계열, qna, wishlist |
| V50~V59 | Wave 3 T1 | store, store_stock, routine 계열 |
| V60~ | Wave 4 | 보정 |

**2. 공통 코드 소유권**: `common` 패키지(ApiResponse, ErrorCode, BusinessException, 전역 핸들러), 루트 빌드 설정, `docker-compose.yml`은 **Wave 0 산출물 이후 동결**. 수정 필요 시 보고만.

**3. 도메인 간 인터페이스**: 타 도메인 접근은 `*QueryService` / `*CommandService` 인터페이스 경유 (CLAUDE.md 규칙). 예: `review`의 구매 인증은 `order.OrderQueryService.hasDeliveredItem(memberId, goodsNo)`를 호출 — Wave 2 T3는 이 인터페이스에 맞춰 개발하고, 실 구현은 T2가 제공(머지 시 결합).

**4. ErrorCode 네임스페이스**: 도메인별 접두사(`MEMBER_`, `GOODS_`, `ORDER_`, `PAY_`, `REVIEW_`, `DLVY_`, `ROUTINE_`, `COMPAT_`)로 enum 상수 추가만 허용(기존 수정 금지).

**5. 테스트 규약**: 단위/슬라이스 = H2(MySQL 모드, Flyway off, ddl-auto=create-drop) — 터미널 병렬 안전. 공유 MySQL·토스 API를 만지는 통합/E2E는 Wave 4 직렬 웨이브에서만.

## 웨이브별 완료 기준 (Definition of Done)

- **W0**: `./gradlew test` 녹색 + 가입→로그인→내정보 조회가 curl로 재현 + 프론트에서 로그인 성공
- **W1**: 카테고리 트리·상품 목록/상세·성분 API가 시드 데이터로 응답 + 프론트 상품카드가 MSW mock으로 렌더
- **W2**: 검색/랭킹/장바구니 API + 토스 테스트 결제 승인-검증 통과(결제 2단계) + 리뷰 CRUD(구매인증 포함, 인터페이스 스텁)
- **W3**: 오늘드림 판정·조건부 차감(동시성 테스트 포함) + 루틴 조회·궁합 진단 + 프론트 탐색 플로우가 실API로 동작
- **W4**: 탐색→루틴 담기→주문→결제 E2E 녹색, admin에서 상품/루틴 CRUD 가능, README에 실행법

## Wave 0 실행 프롬프트 (터미널 1개, 직렬)

```bash
# 1) 계획서 커밋 (이미 커밋돼 있으면 생략)
git add docs/plans && git commit -m "docs(plan): 로드맵 + Wave 0 Foundation 계획"
# 2) worktree 생성
git worktree add "../BeautyBoy-w0" -b feat/foundation
```

새 터미널에서 `cd "../BeautyBoy-w0"` 후 Claude Code를 열고 아래를 붙여넣는다:

```
CLAUDE.md와 docs/plans/2026-07-23-wave0-foundation.md를 읽고, 그 계획서의 태스크를
순서대로 실행해줘. 너는 오케스트레이터다: 태스크마다 서브에이전트(model: sonnet)를 스폰해
TDD로 구현시키고, 태스크 사이마다 테스트 통과와 Files 목록 준수를 리뷰한 뒤 다음으로 넘어가.
전 태스크 완료 후 ./gradlew test와 npm test 결과를 보고해.
```

Wave 1~4 실행 프롬프트는 각 웨이브 상세 계획서 작성 시 그 문서에 포함한다.
