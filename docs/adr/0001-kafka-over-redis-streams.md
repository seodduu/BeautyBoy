# ADR 0001 — 주문 확정 후처리 전달 수단으로 Kafka를 고른다

- **날짜**: 2026-07-29
- **상태**: 채택됨 (구현·측정 완료)
- **관련**: [부하 리포트](../loadtest/2026-07-29-report.md),
  [설계 문서](../plans/2026-07-29-traffic-hardening-design.md) §3·§5

## 맥락

주문 확정(`PaymentService.confirm`) 이후에 해야 하는 일이 셋 있다 — 장바구니 비우기,
판매량 집계 증분, 알림 레코드 적재. 이 셋을 confirm 트랜잭션 안에서 동기로 하면
**알림 INSERT 하나가 실패해도 이미 토스에서 승인된 결제가 롤백된다.** 후처리를 결제에서
떼어내야 하고, 떼어내려면 "확정됐다"는 사실을 전달할 수단이 필요하다.

전달 수단에는 성능 외의 요구가 붙는다.

- **유실 불가**: 결제는 됐는데 장바구니가 안 비워지는 상태가 남으면 안 된다.
- **재시도 가능**: 일시적 실패(DB 락, 커넥션 고갈)는 다시 시도하면 성공한다.
- **실패 격리**: 셋 중 하나가 실패해도 나머지 둘은 진행돼야 한다.
- **주문 단위 순서**: 같은 주문에 대한 이벤트는 순서대로 처리돼야 한다.

그리고 이 프로젝트는 취업 포트폴리오다. **"왜 이 도구인가"를 설명할 수 있는지가
도구 자체만큼 중요하다.**

## 후보 비교

| 기준 | Spring `@TransactionalEventListener` | Redis Streams | **Kafka** |
|---|---|---|---|
| 내구성 | **없음** — JVM 메모리. 프로세스가 죽으면 미처리 이벤트 소멸 | 있음(AOF/RDB 설정에 따라). 단 메모리 우선 저장이라 대량 적체 시 압박 | **디스크 로그가 1차 저장소.** 보존 기간 내 재생 가능 |
| 순서 보장 | 리스너 호출 순서만. 병렬화하면 깨짐 | 스트림 단위 순서. 파티셔닝 개념이 없어 병렬 소비 시 직접 샤딩해야 함 | **파티션 키 단위 순서**(키=orderId → 같은 주문은 항상 같은 파티션) |
| 팬아웃(여러 소비자가 같은 이벤트) | 리스너 여러 개로 가능 | 컨슈머 그룹 여러 개로 가능 | **컨슈머 그룹 여러 개로 가능**(이 프로젝트가 그렇게 씀) |
| 재시도·DLQ | 직접 구현 | 직접 구현(PEL/XCLAIM 조합) | **Spring Kafka 기본 제공**(`DefaultErrorHandler` + `DeadLetterPublishingRecoverer`) |
| 소비 지연 완충 | 없음 | 있음 | **있음**(컨슈머 랙으로 흡수, 랙 자체가 관측 지표) |
| 운영 부담 | **0** — 추가 인프라 없음 | 낮음(Redis는 이미 쓰고 있음) | **높음** — 브로커 추가, 힙·리텐션·파티션 관리 |
| 학습 가치(포트폴리오) | 낮음 | 중간 | **높음** — 커머스 현업의 표준 도구 |

## 결정

**Kafka를 쓴다.** 토픽 `order-events`, 파티션 3, 키 = orderId.

세 후보를 자른 근거는 각각 다르다.

**Spring 이벤트를 자른 이유는 내구성이다.** `@TransactionalEventListener(AFTER_COMMIT)`은
커밋 후에 호출되지만, 그 시점에 JVM이 죽으면 이벤트는 그냥 사라진다. 결제는 커밋됐는데
장바구니가 영원히 안 비워진다. 재시도·DLQ도 전부 직접 만들어야 한다. 운영 부담이 0인 것은
매력적이지만, **"유실 불가"가 이 문제의 1순위 요구**라 후보에서 탈락한다.

**Redis Streams를 자른 이유는 두 가지다.** 하나는 성질 — Redis는 이 프로젝트에서 이미
"없어도 되는 것"으로 쓰고 있다(조회수 버퍼, 캐시 모두 Redis 장애 시 DB 직행 폴백).
같은 인스턴스를 "없으면 안 되는 것"의 저장소로 겸하면 폴백 철학이 깨지고, 캐시가 메모리를
밀어낼 때 이벤트가 함께 압박받는다. 다른 하나는 재시도·DLQ를 PEL(Pending Entries List)과
`XCLAIM`으로 직접 조립해야 한다는 점 — 이 프로젝트의 규모에서 그 코드를 직접 쓰는 것은
Kafka를 붙이는 것보다 오히려 위험하다.

**Kafka를 고른 이유는** 위 네 요구(내구성·재시도·격리·주문 단위 순서)를 **전부 기성품으로**
만족시키기 때문이다. 특히:

- **파티션 키 = orderId** — 같은 주문의 이벤트는 같은 파티션에 떨어져 순서가 보장되고,
  다른 주문은 병렬로 처리된다. Redis Streams에는 이 개념이 없다.
- **컨슈머 그룹 분리로 실패 격리** — `KafkaConsumerConfig`가 `.cart-clear`,
  `.sales-aggregation`, `.notification` 세 그룹을 만든다. 오프셋·재시도·DLT가 그룹별로
  독립이라 알림이 DLT로 가도 장바구니 비우기는 정상 진행된다.
- **DLQ가 설정 몇 줄** — `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`로
  3회 백오프(1s→2s→4s) 후 `order-events.DLT`. 원본 토픽·파티션·오프셋·예외가 헤더에 보존되고
  `POST /api/admin/dlq/replay`가 그 헤더에 기대 재발행한다.
- **파티션 3의 근거**: 단일 컨슈머 인스턴스에서도 파티션별 병렬 소비를 실험할 수 있는 최소 수
  (`KafkaTopicConfig`).

정직하게 덧붙이면, **학습 목적이 이 결정의 진짜 무게추 중 하나다.** 후처리 3종이 지금처럼
가벼운 로컬 DB 쓰기뿐이라면 Spring 이벤트 + 재시도 몇 줄로도 실무적으로 충분하다.
그것을 알면서 Kafka를 고른 것이고, 그 사실을 감추지 않는다.

## 결과

**얻은 것**

- 후처리 실패가 결제를 죽이지 않는다. 세 컨슈머가 서로를 막지도 않는다.
- Kafka가 통째로 죽어도 결제는 커밋된다 — 아웃박스 행이 쌓였다가 릴레이가 복구 후 발행한다.
- 컨슈머 랙이 그대로 관측 지표가 된다. 측정 중 최대 랙 3(540 파티션 샘플 중 70.7%가 0).

**치른 것**

- docker-compose에 브로커 하나가 늘었다(KRaft 단일 노드, 힙 조임). 로컬 개발에서 Kafka 없이도
  앱이 떠야 하므로 `beautyboy.events.enabled` 토글로 릴레이·토픽 선언·리스너 컨테이너를 전부
  껐다 켤 수 있게 했다(기본 false).
- **지연은 사지 못했다.** 부하 리포트 §3.1 — 분산 모형 p95 1,150.63ms → 1,145.44ms(0.45%).
  후처리 3종이 전부 가벼운 로컬 DB 작업이라 애초에 confirm 지연에서 차지하는 비중이 없었다.
  이 결정이 산 것은 성능이 아니라 가용성·정합성이다.
- 집중(단일 SKU) 모형에서는 **7.3% 악화**했다 — 아웃박스 INSERT가 재고 행 락 구간 안에
  추가되기 때문이다(리포트 §3.3, [ADR 0004](0004-stock-lock-contention-out-of-scope.md)).

**운영이라면**: 브로커 3노드 + `replicas: 3` + `min.insync.replicas: 2`다. 지금은 단일 노드
KRaft에 `replicas: 1`이라 **브로커가 죽으면 미소비 이벤트를 잃는다** — 로컬 학습 환경이기
때문에 감수한 것이지, 이 구성이 옳아서가 아니다.
